### 9.1. Идентификация «rule 52» — точная (исправлено 2026-09-07 после возражения пользователя)

**ERRATUM:** в первой версии этого раздела я ошибочно принял экспорт-образец из проекта
(`Imagus_sieve_2026.07.15_823.json`) за живой кэш пользователя и заключил «устаревший сив».
Пользователь обновлял сивы дважды после переустановки — экспорт в проекте хранится как образец,
не как его состояние. Ниже — проверка по ЖИВОМУ upstream-репозиторию.

Воспроизведён алгоритм `cacheSieve` (service.js:215–258) на сиве, скачанном напрямую из
`sieveRepository` по умолчанию — `https://raw.githubusercontent.com/kuzn123/Imagus-Sieve-RuBoard/master/update.txt`
(824 правила после фильтров):

- **rule[52] = `ArtUntamed-g-x`** — актуальная версия, `link: ^(?:artuntamed\.com)/index\.php\?media/(albums/)?[\w.-]+/`.
- Правило двухветочное: **альбомная** ветка (`albums/` в URL, `$[2]`) собирает `data-src` со страницы
  в список-альбом (пагинация по 50, `{loop}`-переходы) — `.author` не читает; **одиночная** ветка
  (прочие `?media/slug/full`) парсит `ld+json → mainEntity` и читает `$.author` **без null-гварда на `$`**.
- **Ошибка «Cannot read properties of null (reading 'author')» — баг АКТУАЛЬНОГО правила**
  (upstream sieve-репозиторий): если на странице-цели нет `ld+json`-скрипта с `mainEntity`,
  `$` = null → TypeError. Не «старый сив» и не код мода. Чинить — в upstream-репозитории сивов;
  со стороны мода корректное поведение — показать падение видимым (BG-2-класс диагностики).
- Из альбомной ветки же следует источник относительных URL: правило возвращает items как
  относительные `/index.php?…/full` (data-src страницы) — прямое подтверждение BG-1.

## 14. BG-4 — корневой механизм «10 из 11 молчат»: дедуп-ключ коллапсирует query-маршруты (ДОКАЗАНО)

**Метод:** реальные функции вырезаны из исходников (техника `md-unit-smoke`) и исполнены на
11 фактических URL галереи ArtUntamed (relative-форма как в Save-логе + absolute-форма как в
Ctrl+Q). Скрипт-доказательство удалён после прогона; результат сохранён здесь.

```
fileKey("https://artuntamed.com/index.php?media/a-flirt…-1.117333/full")  = "https://artuntamed.com/index.php"
fileKey("https://artuntamed.com/index.php?media/a-flirt…-2.117334/full")  = "https://artuntamed.com/index.php"
… все 11 → ОДИН И ТОТ ЖЕ КЛЮЧ
```

**Причина:** `fileKey`/`_normalizeUrlKey` по контракту отбрасывают query-string (давить
cache-buster'ы: `?1234567890` на rule34; регрессионный прогон подтверждает корректность
коллапса для этой задачи). Но у ArtUntamed **весь путь к файлу лежит в query**
(`/index.php?media/slug.NNN/full` — фронт-контроллер), pathname у всех 11 одинаков →
11 разных файлов = 1 ключ. Такая форма встретилась впервые; e-hentai/rule34-формы в
тестах различимы pathname, потому до живого теста не ловилась.

**Полное объяснение обоих логов:**
- Ctrl+Q (21:32): миниатюра #1 (117333) резолвилась мгновенно (hover-кэш) → её ключ лег в
  `downloadAllUniqueUrls`/`globalProcessedUrls` первым → [006] скачана. Ключи #2–11 = дубликат
  → `continue` в onResolved (content, до SW) и/или «Duplicate (same file)» в processFilterQueue
  (SW:729–736, skipped++ без progress-записи) → **10 молчаливых смертей**. В логе 5 skipped —
  все «Too small» (обвязка), т.е. смерти BG-4 в лог НЕ попали вовсе.
- Save All (21:46): `seen` в doSave строится `_normalizeUrlKey` → ключ #1 выжил →
  downloadMass → FAILED «Failed to fetch» на ОТНОСИТЕЛЬНОМ URL (BG-1) = [001]; ключи #2–11 =
  дубликат → молчаливый return (content.js doSave). Ровно 1 запись, 10 исчезли, при том что все
  11 превью были прогружены (пользователь подтверждает).

**Ключевая коррекция, сделанная пользователем (не пропускать при восстановлении контекста):**
превью галереи грузятся лоадером с resolve-каскадом (постройка для rule34, последний релиз) →

  записи лейблов). Гварды: (1) re-entry в `doSave`: `if (saving) return;` первой проверкой;
  (2) `updatePanel`: при `saving` обновить только подпись Select all и вернуться, НЕ трогая
  `disabled`/текст Save-кнопок (они держат «Resolving…»/disabled от `doSave`).
- Сопутствующая правка (обязательная): `buildPanel` создаёт `bSave` без текста — лейбл ставит
  только `updatePanel`; при закрытии/открытии галереи ВО ВРЕМЯ Save новый бар под гвардом получил
  бы ПУСТУЮ кнопку Save Selected. Добавить инициализацию `bSave.textContent = 'Save Selected'`
  рядом с `bSaveAll.textContent = 'Save All'` (строка 385).
- Проверка последствий в комплексе:
  - `toggleAll` вызывает `updatePanel` — тот же гвард, лок не ломается.
  - Закрытие галереи во время Save (state 2→0→2): `hidePanel(true)` зануляет `panel`/`cellCount`/
    `selected`, но `doSave` держит локальные `saveBtn`/`saveAllBtn` (detached-ноды — запись
    безвредна), а замыкание живёт до конца вкладки: `finish()`-цепочка всё равно доедет до
    `afterReports` и снимет `saving`. В `hidePanel` флаг сбрасывать НЕЛЬЗЯ: скрытие галереи не
    отменяет полёт (abort-пути нет, чанки продолжают уходить) — сброс в `afterReports` покрывает
    оба сценария (открытая и закрытая галерея) одним путём.
  - **Recovery-анализ (fail-closed):** `doSave` не обёрнут в try/catch; сегодня пользовательский
    клик по чекбоксу «случайно» разлачивал кнопки при застывшем `finish()`. С гвардом этот путь
    исчезает: при патологическом зависании `_mdChain` (не зарегистрировано ни разу) кнопки
    останутся залоченными до перезагрузки страницы. Это лучше аварийного разблока (который давал
    дубль-скачивания), но осознанное решение — зафиксировать в комментарии кода.
  - `saving` объявлен в замыкании `_mdGalleryInstall` (устанавливается один раз на page-load,
    `setTimeout(_mdGalleryInstall, 0)`), значит флаг ОДИН на страницу; все пути установки/сброса
    в том же замыкании — второго экземпляра не существует. `decorate()` строит новый бар на новом
    гриде, но живёт в том же замыкании.
  - `updatePanel` выходит по `!panel` (строка 362) до кнопок — при скрытой галерее гвард не нужен.
- Альтернатива, отклонённая: лочить весь бар (pointer-events:none) — ломает UX (нельзя менять
  выделение во время Save) и не чинит re-entry через чекбокс (чекбоксы не в баре). Гвард-флаг —
  минимальное решение.
- Тест-план после правки: (1) большой links-батч (e-hentai /g/ из §18) → во время «Resolving…»
  клик чекбокса → кнопки НЕ активируются, повторный Save-клик игнорируется; (2) обычный Save с
  превью → «Queued ✓» → через 1.5s updatePanel восстанавливает подпись и активность; (3) закрытие
  галереи во время Save → повторное открытие → Save работает (флаг снят в afterReports), кнопка
  Save Selected нового бара НЕ пустая (инициализация в buildPanel);
  (4) `md-marker-check` 5/5×2 + `node --check` (smoke не задет).
