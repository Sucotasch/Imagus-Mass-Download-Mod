## 14. BG-4 — корневой механизм «10 из 11 молчат»: дедуп-ключ коллапсирует query-маршруты (ДОКАЗАНО)

**Метод:** реальные функции вырезаны из исходников (техника `md-unit-smoke`) и исполнены на
11 фактических URL галереи ArtUntamed (relative-форма как в Save-логе + absolute-форма как в
Ctrl+Q). Скрипт-доказательство удалён после прогона; результат сохранён здесь.

```
fileKey("https://artuntamed.com/index.php?media/a-flirt…-1.117333/full")  = "https://artuntamed.com/index.php"
fileKey("https://artuntamed.com/index.php?media/a-flirt…-2.117334/full")  = "https://artuntamed.com/index.php"
… все 11 → ОДИН И ТОТ ЖЕ КЛЮЧ
```

**Причина:** `fileKey`/`_normalizeUrlKey` по контракту отбрасывают query-string (давить
cache-buster'ы: `?1234567890` на rule34; регрессионный прогон подтверждает корректность
коллапса для этой задачи). Но у ArtUntamed **весь путь к файлу лежит в query**
(`/index.php?media/slug.NNN/full` — фронт-контроллер), pathname у всех 11 одинаков →
11 разных файлов = 1 ключ. Такая форма встретилась впервые; e-hentai/rule34-формы в
тестах различимы pathname, потому до живого теста не ловилась.

**Полное объяснение обоих логов:**
- Ctrl+Q (21:32): миниатюра #1 (117333) резолвилась мгновенно (hover-кэш) → её ключ лег в
  `downloadAllUniqueUrls`/`globalProcessedUrls` первым → [006] скачана. Ключи #2–11 = дубликат
  → `continue` в onResolved (content, до SW) и/или «Duplicate (same file)» в processFilterQueue
  (SW:729–736, skipped++ без progress-записи) → **10 молчаливых смертей**. В логе 5 skipped —
  все «Too small» (обвязка), т.е. смерти BG-4 в лог НЕ попали вовсе.
- Save All (21:46): `seen` в doSave строится `_normalizeUrlKey` → ключ #1 выжил →

### 22.6. P-1: адаптивный режим page-fetch по хосту — дизайн (утверждено 2026-09-09)
**Проблема (лог 16-19-35):** каждая wimg-строка начинается с `GET/403 → referer retry
failed: Failed to fetch` (~80 раз за сессию) — обречённый page-fetch с `credentials:'include'`.
При credentials-режиме `Access-Control-Allow-Origin: *` неприменим (wimg, вероятно, отдаёт
именно `*`) → fetch отклоняется ДО запроса, ~0.2–0.5 с чистых потерь на каждый файл. Same-host
URL (`rule34.xxx//images/...`) проходят этот путь успешно ([005]–[007] REFERRER/200) —
обречена именно credentialed-попытка на кросс-домен.

**Машина состояний на хост (сессия, `refererHostModes[host]` в service-init):**
- `undefined` — не зондировали: page-fetch идёт с `credentials:'include'` (текущее поведение);
- `'omit'` — include умер транспортной ошибкой ('Failed to fetch'/'NetworkError', НЕ HTTP-код
  и НЕ 'Too large'): перезапуск page-fetch с `credentials:'omit'` (Referer браузер приложит сам
  по referrerPolicy; меняется только отсутствие cookies; `ACAO:*` для omit валиден);
- `'browser'` — обе попытки транспортно мертвы: хост навсегда (до сброса сессии) минует
  content-fetch — задача уходит прямо в `chrome.downloads` (build задачи = переиспользование
  живого filter-task, `filterMethod='BROWSER'`, попытка пишется в цепочку).

**Точки касания:** `triggerRefererDownload` (режим browser → прямой пуш в downloadQueue;
payload +`mode`), `handleRefererDownloadFailed` (include-транспорт-фол → записать попытку,
перевести хост в 'omit', re-trigger; omit-транспорт-фол → 'browser', существующий
browser-fallback; HTTP-4xx/5xx и Too large → существующие пути без изменений),
`handleRefererDownloadReady` — БЕЗ правок (успех include оставляет хост в undefined =
следующие URL снова include; успех omit оставляет 'omit'). Content `_downloadWithReferer`:
`credentials: d.mode === 'omit' ? 'omit' : 'include'` (content.js + content-block.js, оба
дерева). Сброс: `resetMassDownloadSession` чистит режимы.

**Watchdog-гонка (ключевой нюанс):** re-trigger при том же URL заново добавляет его в
`refererRetryUrls` и вооружает ВТОРОЙ watchdog — первый (30 с от include-попытки) увидел бы
URL в сете, украл бы слот omit-попытки и пометил бы её 'timed out' (утечка activeRefererRetries
— session никогда не дренируется). Решение: `refererAttemptSeqMap` (url→номер попытки),
watchdog срабатывает только если его номер актуален; готовность/фолл не трогают мапу

### 24.2. Почему Referer нельзя поставить в существующих путях

- `fetch()` в SW: «Referer» — forbidden header name (Fetch spec); Chrome молча
  игнорирует его — что и наблюдаем в `GET/403`.
- `chrome.downloads.download`: API не принимает заголовки вовсе.
- Page-context fetch (P-1): CORS — i.pximg.net не даёт ACAO, запрос не выходит.
- Единственный привилегированный механизм расширения — **declarativeNetRequest**
  session rules: modifyHeaders, Referer подставляется сетевым движком Chrome
  (не из JS), гейт такой запрос пропускает. Прямой аналог GM_xmlhttpRequest.

### 24.3. Дизайн Fix E (утверждён пользователем)

- **Реестр, не blanket-правило:** `MD_DNR_MEDIA_HOSTS` в новом модуле
  `mass-download/md-dnr.js` — только хосты с доказанным Referer-гейтом
  (`i.pximg.net`, `i-f/i-cf/i-og.pximg.net` → fallback `https://www.pixiv.net/`).
  Хост вне реестра → поведение не меняется вовсе.
- **Значение Referer:** `task.referer` (страница, где найден URL — доказанно проходит
  гейт: попап `<img>` шлёт Referer именно этой страницы); fallback — корень сайта из
  реестра (когда referer нет — попап-сейв). Non-http(s) referer заменяется fallback.
- **Скоуп правила:** condition `urlFilter: '||host^'` + `initiatorDomains:
  [chrome.runtime.id]` — правило действует ТОЛЬКО на запросы, инициированные нашим
  расширением. resourceTypes намеренно опущены (запросы chrome.downloads не
  типизированы как xmlhttprequest). Один session rule на хост, стабильные id 1..N.
- **Время жизни:** session rules переживают засыпание SW, стираются браузером при
  завершении сессии; повторный add того же id перезаписывает (идемпотентно).
  `mdDnrRearm()` на старте SW подмечает уже-установленные правила (чистая оптимизация).
- **Best-effort:** недоступность DNR (старый Chrome/FF, нет permission) →
  деградация к поведению до Fix E, ничего не ломается.
- **Куда встроено (5 хуков, оба дерева):**
  1. `processFilterQueue` — await ensure перед HEAD-валидацией (главная точка:
     правило стоит до первого запроса);
  2. GET-фоллбек — повторный ensure (дёшево, идемпотентно);
  3. `processDownloadQueue` — ensure перед `chrome.downloads.download` для задач,
     не прошедших фильтр (BROWSER-путь advanceToNextCandidate);
  4. upstream `case "download"` (попап-сейв) — fire-and-forget ensure;
  5. upstream `onChanged` alterDownload-ветка — ensure при SERVER_FORBIDDEN-обрыве
     (сейв попапа до всякого скана: правило не стояло при старте загрузки).
- **Манифест:** `permissions += "declarativeNetRequest"` (host_permissions
  `<all_urls>` уже есть — покрытие хоста для modifyHeaders достаточно).

### 25.2. Причина (документация Chrome RuleCondition + лог)

1. Правило БЕЗ `resourceTypes` матчит все типы, КРОМЕ `main_frame` — это
   документированное поведение сокращённой формы.
2. Запрос downloads-API не типизирован как xmlhttprequest и/или не несёт
   инициатора расширения (`initiatorDomains` фильтрует по инициатору запроса,
   не по URL).

Оба условия v7 закономерно отсекали download-запросы.

### 25.3. Решение (Fix E-2, «A» из одобренного дизайна)

`mdDnrBuildRule`: явный список `resourceTypes` — все 14 документированных типов
включая `main_frame` (общий знаменатель с движком Firefox); `initiatorDomains`
убран. Правило по-прежнему реестр- и сессия-ограничено, подставляет только
Referer. Побочный эффект (принят пользователем): правило срабатывает и на
чужие запросы к pximg-хостам — хотлинки с других сайтов грузятся вместо 403.

**Архитектурное решение — без байтового буферизующего яруса.** В ходе
проектирования рассматривался «C-резерв» (SW fetch → blob → object URL →
downloads), реализованный и ОТКАЧЕННЫЙ в тот же день по итогам ревью:

- Blob не пересекает JSON-границу мессенджинга расширения Chrome (structured
  clone — только Chrome 148+ по opt-in; официальный блог Chrome
  «Unlock Structured Clone for Chrome Extension Messaging»);
- в MV3 SW нет `URL.createObjectURL` (требует DOM; how7o/Chromium issue
  40876652);
- pixiv PNG — 30-40 MB: буферизация через кучу SW — неправильная архитектура
  (data:-URL раздувает байты на ~33%, перенос в offscreen-документ — новая
  permission и новый файл);
- браузерный download под расширенным правилом **стримит любой размер, не
  буферизуя ни байта** — это и есть механизм референс-скрипта (правильный
  Referer едет с запросом), переведённый на рельсы расширения.

Механика как у референс-скрипта (greasyfork 39387): его GM_xmlhttpRequest —
привилегированный фетч с Referer; расширение не может дать fetch'у SW
настоящий Referer-заголовок (forbidden header), но DNR-правило достигает того
же эффекта на уровне сети — для ВСЕХ привилегированных контекстов, включая
браузерные download-запросы.

> намерение — нет. Практический риск: читатель делает вывод «Referer уходит с
> SW-запросом» и при рефакторинге удаляет `md-dnr.js` как «дублирующий
> механизм» — после чего пикси-класс ломается молча (403). Живой механизм —
> **только DNR-правило**. В остальном таблица §26.2 подтверждена аудитом.

### 26.3. Firefox-баги: корневая причина — мёртвый event page

Пользователь: «ещё с прошлого релиза версия расширения для Firefox не
работает, не запрашивает разрешения на пользовательские скрипты, не

`background: {scripts}` — это **event page** (window-контекст), где

требует живого фона для round-trip `checkUserScripts`), нет
`openOptionsPage`, нет обработчиков сообщений, нет контекстных меню.

именно в v2026.8.20.7, потому что Fix E добавил туда третий импорт (и до
этого FF-дерево просто ни разу не тестировали живьём).

> Второе утверждение этого абзаца **НЕВЕРНО** — оно противоречит git. Ошибочно:
> «убила расширение именно в v2026.8.20.7». На самом деле строка `importScripts(...)`

### 26.5. FF Fix 2 (Referer): нативные headers в downloads.download

Firefox (70+) — единственный браузер, где downloads API **разрешает
Referer** в `headers` ([MDN](https://developer.mozilla.org/docs/Mozilla/Add-ons/WebExtensions/API/downloads/download)).
Ровно та же семантика, что у userscript-референса: правильный Referer едет
с запросом, ни один байт не буферизуется в фоне. DNR-правило остаётся
(безвредно, всё ещё прикрывает HEAD-валидацию в SW-фети).

Два места (оба — canonical delta-файлы):

1. `mass-download/service-core.js` → processDownloadQueue: для
   registry-хостов (через `mdDnrRequestFor`) добавлен
   `headers: [{ name: "Referer", value: mdDnrReq.referer }]`, гвард
   `platform === "firefox"`, blob/object-URL не тронуты.
2. `background/service.js` → download (popup-save): тот же
   registry-lookup и заголовок в `params.headers`.

> **УТОЧНЕНИЕ СТАТУСА 2026-09-11 (аудит `BT-12`).** Формулировка «правильный
> Referer едет с запросом» — **гипотеза, а не установленный факт**: это
> единственная часть FF-дельты, не подтверждённая живым прогоном. §26.8 сам
> фиксирует «Pixiv на FF: в лог ничего не попадает» — то есть ровно тот класс
> хостов, ради которого Fix 2 написан, на FF живьём **не доказан**. Совместимость
> по MDN (Firefox 70+ разрешает `headers` в `downloads.download`) — условие
> необходимое, но не достаточное. До живого прогона (FF → pixiv → прогрев →
> прогресс-таб) считать Fix 2 **открытой задачей `BT-12`**, а не закрытым фиксом.
> Код при этом корректен и на Chrome не исполняется
> (гвард `platform === "firefox"`), регрессии не создаёт.

> «форма = признак ДРУГОЙ res-функции → значит в FF другой живой сив» **не
> отменена, но перестала быть главным объяснением**: аудит нашёл
> **верифицированный in-repo механизм**.
>
> - `content/content.js:4427` вызывает `rule.res.call(PVI, d.params)` — значит
>   `this` внутри правила это `PVI`, а `this.res` в правиле — это **общий
>   глобальный `PVI.res`**, один на все правила и все резолвы content-скрипта.
>   Он **не очищается** ни перед вызовом `rule.res`, ни в общем `catch`
>   (`content.js:4429-4433` делает `return 1` без очистки). Любой прерванный
>   `{loop}`-резолв оставляет аккумулятор заполненным, и следующий резолв
>   **любого** правила стартует не с пустого массива, а с остатков прошлого
>   прогона. Это ровно механизм «отравленного альбома» — примесь
>   прошлого/чужого резолва. → **`BT-01` (P1)**, готовый фикс — в аудите.
> - Синхронный XHR в бандловом правиле (`data/sieve.json`, ветка `/g/`) **без
>   per-link `try/catch`** — конкретный источник throw, который оставляет
>   `PVI.res` грязным. → **`BT-02` (P1)**.
>
> Что подтверждено **независимо** (и это усиливает вывод, а не ослабляет его):
> `processLink` пушит только `[matches[1]]` — то есть `[hath_url]`, поэтому
> бандловое правило **действительно не может** дать форму «item с превью +
> сырые /s/». Вывод «это результат другого резолва» сохраняется; «другой
> **сив**» — лишь один из вариантов, теперь есть второй, in-repo:
> **загрязнение из предыдущего/чужого резолва через общий `PVI.res`**. Проверка
> одна и дешёвая (см. §28.3). Пункт 27.6 п.1 остаётся валидной **независимой**
> проверкой.

### 29.3. Chrome rule34: 19 `pending` + пустой лог = **рестарт service worker**

В `Empty log …18-20-54.txt`: `Session start: -` и все счётчики нулевые. `sessionStartTime`
присваивается **только** в `resetMassDownloadSession()` (`service-core.js:287`), а его вызывает любой
старт сессии (`openDownloadProgress` из `PVI.downloadAll` и из Gallery Save). Значит лог отдал
**свежий инстанс SW**, который сессии не начинал: очереди и `downloadProgress` потеряны, а 19 строк
в UI — **устаревший DOM страницы прогресса** (полный mirror приходит только по `registerProgressTab`,
т.е. при загрузке страницы). Очереди не персистятся (известное ограничение MV3), поэтому UX
неотличим от «завис навсегда».

Чтобы назвать причину смерти SW (не угадывать), нужны: консоль SW (`chrome://extensions` →
«service worker») в момент залипания и снимок глобалов:

```js
({scanInProgress, activeDownloads, activeFilters, activeRefererRetries,
  filterQueue: filterQueue.length, downloadQueue: downloadQueue.length,
  rows: Object.keys(downloadProgress).length, sessionId, started: sessionStartTime})
```

Если SW жив и `downloadQueue`=19 при `activeDownloads`=3 — это **утечка слота** (другой дефект,
диагностируется там же); если снимок пуст/свежий — подтверждается рестарт.

### 30.5. Решения по итогам прогона (2026-09-11)

**Лимит тира: `MAX_OFFSCREEN_FETCH` 10 MiB → 32 MiB** (решение пользователя).
Обоснование — **замер**, а не ощущение: по всем сохранённым логам извлечено 773 строки с размером,
максимум **29.97 MB**, выше 32 MiB — **ноль**; с прежним лимитом **15** элементов молча подменялись
уменьшенными производными. `MAX_FALLBACK_SIZE` (10 MiB) и `MAX_PAGE_FETCH` (10 MiB) **остаются 10 MiB** —
они ограничивают кучу, которую мод сам наливает и сливает (SW/страница), а offscreen-байты уходят в
`chrome.downloads` как blob, поэтому число диктуется медиа. Расхождение **намеренное** и закомментировано у константы (плюс лок smoke запрещает «выравнивать» его обратно).

Память: потолок `3 × 32 MiB` ≈ 96 MB в куче offscreen-документа (3 = `maxConcurrentDownloads`),
освобождается по каждому файлу сразу через `mdOffscreenRevoke` в `releaseDownloadSlot`, полностью —
через 30 с после последней задачи (`window.close()`). Оговорка: пик на один элемент может коротко
доходить до ~2× (сборка `Blob` может копировать буферы — **не проверялось**).

**Латентный дефект idle-close — исправлен** (найден чтением кода, в прогоне не проявлялся).
`armIdleClose()` вызывался только при приходе `mdOffscreenFetch`, поэтому пауза > 30 с при ещё идущей
blob-загрузке закрывала документ и обрушивала его blob-хранилище — то есть могла оборвать активную
загрузку. Теперь `liveObjectUrls` инкрементируется в `createObjectURL` и декрементируется по
`mdOffscreenRevoke`; пока счётчик не ноль, idle-таймер перезаряжается вместо закрытия;
`HARD_LIFETIME_MS` (5 мин простоя с живыми URL) — выход для случая, когда SW умер, не отозвав URL.
Таймер дополнительно взводится при загрузке документа, поэтому документ, созданный и не использованный,
тоже закрывается. Локи: `liveObjectUrls`/`idleWithBlobsSince`/`HARD_LIFETIME_MS` в smoke.

**Побочно: rule34 больше не воспроизводится.** `log/Rule34 imagus-mass-download-log-2026-09-11T20-07-34.txt`: `downloaded=42` (было 21), строк `pending` — **0** (было 19 «навсегда»), лог сохранился непустым (`Session start: 2026-09-11 20:06:29`). Единственное изменение этого класса в сборке — гвард `_interruptHandled` (§30.1): без него `state`- и `error`-дельты давали **двойной `advance`** по цепочке одного элемента. Причинность **не доказана** (симптом не воспроизводится = нечего проверять), но при рецидиве смотреть первым делом сюда; в логе этого прогона 62 строки `FAILED` — это откаты по мёртвым кандидатам (норма, FIX-2), а не залипание.
