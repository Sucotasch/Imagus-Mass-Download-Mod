## A. «На странице прогресса одни ошибки» (Ф1, Ф2, Ф11, Ф12)

**Проблема.** Таблица — скользящее окно на 100 строк; волна сбоев в конце сессии вытеснила 291
успешную строку, и страница показывает «Completed in List 0 / Failed 100». Живой счётчик
`downloaded=` есть только в Saved Log.

**Решение (низкая цена, ноль функциональных потерь):**

- **A1.** Плитка **Downloaded** (`#stats-downloaded`) рядом с «Skipped»: значение из
  `stats.downloaded` (данные уже приходят). Она не зависит от вытеснения и отвечает на вопрос
  «сколько реально скачано» без открытия лога. `options/download-progress.html` + `updateGlobalStats()`.
- **A2.** `updateListNote()` печатает живые числа прямо в примечании:
  `Showing the last N records — downloaded=X, skipped=Y this session; the oldest FINISHED rows
  drop off first, so “Completed in List 0” does not mean 0 files.` Формулировка строится из
  `downloadStats`, которые уже есть в области видимости.
- **A3.** Если среди видимых `failed` есть строки с `pickReason = breaker-open…`, примечание
  добавляет одну строку-объяснение (см. B4) — «эти строки не проверялись, хост отказывал».

**Почему не «менять правило вытеснения».** Текущее правило — честное скользящее окно (Ф11);
любая «защита Completed-строк» вернёт перекос в другую сторону. Пояснение + живой счётчик решают
задачу без новых инвариантов.

**Гейт:** `repro-row-window` (уже есть) — новые проверки на текст примечания с числами и на
плитку; лок в `tools/md-unit-smoke.mjs` на формулировку; мутация «примечание молчит при
`failed>0`» должна кусаться.

## B/G. Хост начал отказывать ⇒ расширение долбит его сильнее (Ф2, Ф5, Ф14–Ф17)

### B.0 Что именно показал лог (это не «мёртвые ссылки»)

По цепочкам `attempts` (Ф14) картина такая: наш fetch в фильтр-фазе получает `403`, хост уже
`pinned to browser` (пин по транспортным смертям, Ф17), браузерная загрузка **настоящего** URL
отдаёт `SERVER_FAILED` (429/5xx), угаданные `.jpg` — 404, и даже собственная sample-URL элемента
отдаёт 404. То есть **сайт начал отказывать уже отработанным URL** после ~291 успешной загрузки,
а наше поведение после этого: 8 кандидатов на пункт без пауз и без учёта отказов download-фазы
(Ф16) — это множитель, превращающий один отказ в сотни запросов.

### B.1 Чего мы **не** можем (поправка к постановке вопроса)

«Определять ограничение сайта на одновременную загрузку» — нельзя. Один отказ (429/404/5xx на
URL, работавший минуту назад) не говорит, ЧТО именно исчерпано: параллелизм, частота запросов или
квота за окно. Найти лимит можно только перебором — то есть намеренно провоцируя блок (и
`403` в фильтр-фазе против `429/5xx` в загрузке как раз показывает, что блок не сводится к
параллелизму: последовательные попытки внутри ОДНОГО пункта получают тот же отказ). Поэтому:
**не измеряем лимит, а реагируем на отказ** — и читаем прямую инструкцию сервера, если она есть
(`Retry-After`, `X-RateLimit-Reset` в HTTP-ответах; сейчас мы их не смотрим).

### B.2 Ключевой факт: сегодня breaker вообще НИЧЕГО не приостанавливает

`mdBreakerIsOpen()` вызывается ровно в одном месте — `findBestUrlWithValidation` (`service-core.js:3011`),
то есть влияет только на валидацию группы. Фильтр-фаза и загрузка **не знают о breaker'е вообще**:
в логе каждый пункт всё равно начинает с `GET/403` (фильтр-фаза), а затем идёт в браузерную загрузку.
Итог при шторме — **максимальный объём запросов при нулевой вероятности успеха**. Пауза в 30 с,
которую я предлагал в первой версии плана, была бы *добавлением*, а не сегодняшним поведением — и как
**первая** реакция она неверна: пользователь прав, ждать без результата хуже, чем честно остановиться.
Первая версия (ступени 0→1→2 с авто-замедлением) отозвана: она меняет одно ожидание на другое.

### B.2′ Решение: карантин хоста **без ожидания** + решение за пользователем

Ранжировано по скорости реакции: сначала мгновенные действия, пауза — только по инструкции сервера
или по кнопке пользователя.

- **G1 (мгновенно, дёшево). Классификация отказа.** Хост считается «отказывающим», если один и тот же
  серверный вердикт пришёл по **≥3 РАЗНЫМ пунктам** этого хоста (а не по трём кандидатам одного
  пункта), либо 404 пришёл по URL, который страница сама показала/подтвердила (`mdOk`). Одиночный
  битый URL хост не роняет — это главная защита от ложных срабатываний.
- **G2 (мгновенно). Карантин без сна.** Остаток пунктов хоста → `skipped` с причиной и **Retry**;
  никаких таймеров; остальные хосты и вся остальная работа продолжаются на полной скорости.
  **Сессия становится КОРОЧЕ, а не длиннее:** сегодня 100 пунктов × (GET + до 8 загрузок) ≈ 800
  запросов и 0 результата; с карантином — 1–3 запроса и понятное сообщение.
- **G3. Никаких пауз «наугад».** Пауза допускается только: (a) если сервер сам назвал срок
  (`Retry-After` — показываем обратный отсчёт **и всё равно даём кнопку «не ждать»**, чтобы паузу
  выбирал пользователь, а не мы за него), (b) внутри пользовательского медленного режима (G4).
- **G4 (по кнопке). «Retry these slowly».** В окне прогресса рядом со строками карантина: 1 запрос
  за раз, ~2 с между запросами, при **первом же** отказе — мгновенный стоп с отчётом
  («всё ещё отказывает: 1 запрос, 1.4 с»). Худший случай — секунды, а не 30 с. Эскалация паузы
  внутри этого режима (2 с → 5 с) только если пользователь нажал повторно.
- **G5 (бесплатно). Поздний re-probe.** Когда остальная очередь опустела, один запрос на карантинный
  хост: прошёл — скачиваем отложенные пункты (в медленном режиме), нет — сообщение. Стоит 1 запрос
  и использует время, которое уже потрачено на остальную работу.
- **G6 (множитель).** Пока хост в карантине, цепочки кандидатов/тиру для него не запускаются вообще
  (иначе 1 отказ = 8 запросов × N пунктов).
- **G7 (обратная связь).** Для G1 нужны отказы **download-фазы** (сейчас она не влияет на хосты —
  Ф16: «291 скачано, потом 284 отказа без реакции»). Сигнал — серверные вердикты
  (`SERVER_FAILED`/`SERVER_FORBIDDEN`/`SERVER_BAD_CONTENT`); `timeout`/`network-error` — **не** сигнал.
- **G8 (`Retry-After`).** Читается там, где мы видим заголовки: фильтр-фаза и offscreen-тир
  (в offscreen уже есть `res.status`, добавить `retryAfter`). Browser-загрузка заголовков не отдаёт.
- **G9 (тексты).** `mapDownloadInterruptReason('SERVER_FAILED')` → без выдуманного кода:
  `'Server refused the download (HTTP error other than 403/404 — often 429 rate limiting or 5xx)'`;
  `mdItemFailedText` для карантинных строк добавляет
  `'— the host was refusing requests; this is not a dead link, press Retry later'` (это и снимает
  «стену ошибок» из пункта A).
- **G10 (видимое предупреждение).** Строка состояния на самой странице + блок в окне прогресса + Saved Log:
  «<host> отказал: N пунктов отложены (после M успешных загрузок). [Retry slowly] [Retry later]»
  — решено пользователем: показывать и на странице, а не только в служебном окне.

### B.3 Цена (посчитано, не на глаз)

Живой прогон: 291 файл за ~11 минут (16:01:01 → 16:12:07) при 3 параллельных загрузках ≈
**26 файлов/мин**. Что меняется в бюджете времени:

| | Сегодня | С карантином (B.2′) |
|---|---|---|
| Запросов на «мёртвой» части сессии | ~800 (100 пунктов × GET + до 8 загрузок) | 1–3 (классификация) + 1 (поздний re-probe) |
| Время на эти 100 пунктов | минуты, 0 результата | секунды, результат — сообщение + Retry |
| Остальные хосты | ждут в общей очереди | идут параллельно без пауз |

То есть время сессии **уменьшается**, а не растёт: отброшено именно то, что сейчас съедает минуты без
результата. Медленный режим (G4) — по запросу пользователя, его цена честно показывается
(~30 файлов/мин при живом хосте: 1 за раз + 2 с).

**Честное ограничение:** если у сайта жёсткая квота на окно (данные намекают: блок начался после
~291 файла и за 11 минут не отпустил), остаток в этой сессии не вернуть никаким пейсингом. Поэтому
правильный исход — сообщить и дать выбор (G2/G4/G5), а не молчаливое ожидание.

### B.4 Гейт

Новый исполняемый харнесс `repro-host-quarantine` на **реальных** функциях обоих деревьев
(заглушки `validateSingleUrlContent` и `chrome.downloads`, счётчик запросов к хосту):
(a) один отказ пункта ⇒ хост жив, цепочка кандидатов обычная;
(b) 3 РАЗНЫХ пункта с одним серверным вердиктом ⇒ карантин: **ноль новых запросов** к этому хосту,
строки `skipped` с причиной и Retry, загрузки с **другого** хоста при этом продолжаются
(это и есть «сессия не ждёт»);
(c) у карантинного хоста цепочка кандидатов/тиру не запускается — счётчик запросов остаётся 1–3, а
не 8×N (мутация «снова гонять все кандидаты» должна кусаться);
(d) 3 отказа по трём кандидатам ОДНОГО пункта карантин **не** включают (защита от ложных);
(e) 8 таймаутов/сетевых ошибок карантин не включают;
(f) `Retry-After: 120` ⇒ пауза 120 с только для этого хоста + видимый отсчёт + кнопка «не ждать»;
(g) медленный режим: первый же отказ ⇒ ровно 1 запрос и стоп (мутация «продолжает долбить» кусается);
(h) поздний re-probe: успех ⇒ отложенные пункты скачиваются; отказ ⇒ 1 запрос и сообщение;
(i) карантина нет ⇒ поведение прежнее байт-в-байт.
Плюс локи в `md-unit-smoke` (оба дерева) и мутации в `mutation-check`.

## R. Массовый Retry: одна кнопка вместо сотни (по замечанию пользователя)

**Проблема.** Поштучный Retry в окне прогресса — плохой UX: после карантина там может оказаться
200 строк, а большинство пользователей это окно вообще отключают (`showProgressTab`) — оно нужно
нам для разработки. Ожидание пользователя — «нажал один раз, и всё скачалось». Сейчас:
- в попапе **одна** кнопка (`popup.html:62`) и никакого retry;
- `handleRetryDownload` — поштучный (`msg.url`), он же поднимает сессию (`scanInProgress = true`)
  и снимает флаги отмены, но **теряет цепочку кандидатов** (в фильтр-очередь идёт один URL);
- после «пустого» дренажа снимок сессии выбрасывается (FIX-7), поэтому после перезапуска SW
  повторять нечего даже в окне прогресса.

**Решение: одна кнопка «Retry not-downloaded (N)».**

- **R1 (где).** **Три носителя одного и того же состояния** — потому что при запуске по хоткею попап
  закрыт и вообще не открывается:
  1. **строка статуса на странице** — главный носитель для хоткей-пользователя: с числом и **кнопкой**
     прямо там (сейчас `_stopKeepAwake` показывает зелёный текст всего 5 с и говорит только «сколько
     найдено», ничего не зная о скачанном — см. R8);
  2. **попап** — та же кнопка при следующем открытии (по персистентному состоянию, R11);
  3. **окно прогресса** — для нас.
- **R2′ (что берёт — решено).** `failed` + карантинные `skipped` + `canceled` из-за новой сессии (C1).
- **R2 (что).** Кнопка берёт **все пункты без файла**: `failed` + карантинные `skipped` (новый
  флаг) + `canceled` из-за новой сессии (C1). **Не** берёт `superseded` (это альтернативные
  кандидаты уже скачанных пунктов — повтор = дубликаты) и не берёт фильтр-скипы (размер/тип).
- **R3 (как).** Один вызов разворачивается в цикл по тому же **существующему** поштучному пути
  (`handleRetryDownload`): подъём сессии, снятие флагов, keepalive, исключение из дедупа — всё
  сохраняется. Дополнительно на карантинных строках сохраняется остаток `_candidates` (`retryCandidates`),
  чтобы повтор шёл по цепочке, а не по одному URL (иначе теряется случай «верхний URL 404 → файл в
  следующем кандидате»).
- **R4 (самоуправление).** Массовый retry **сам** запускает карантинный хост в медленном режиме
  (G4): 1 запрос за раз, при первом отказе — стоп и сводка: «Повторено N: скачано X, всё ещё
  отказывает Y (сайт ограничивает)». **Никаких поштучных нажатий**, пауз «в никуда» и повторных
  штормов.
- **R5 (основная кнопка умнеет — решено).** Если есть нескачанные пункты, основная кнопка сначала
  предлагает **«Докачать остаток (N)»**, а полная перекачка с `(1)`-копиями становится вторым,
  вторичным действием. Хоткей `Ctrl+Q` при этом **не меняется** (это «скачать всё с этой страницы»;
  менять его смысл скрытно — ломать предсказуемость); докачка живёт на кнопке в статусе страницы,
  в попапе и в окне прогресса.
- **R6 (выживание после смерти SW).** Снимок сессии не выбрасывается, пока есть нескачанные пункты
  (сейчас `mdFlushSession` сбрасывает его после дренажа), плюс в снимок добавляется фаза, чтобы
  восстановление **не** заказывало странице пересканирование (RESUME-1). Сброс снимка — при явном
  «Clear all», старте нового скана или успешном полном retry.
- **R7 (итог).** По завершении — одна сводка: сколько взято в повтор, сколько скачалось, сколько
  осталось и по какой причине (то есть тот же «один результат», которого ждёт пользователь).

### R.0 Безголовый запуск (хоткей; попап закрыт) — что добавилось после замечения пользователя

- **R8 (сейчас страница не знает правды).** `_stopKeepAwake(finalMessage)` (content.js) печатает
  «Analysis complete. Found N total items» и **убирает элемент через 5 с**. При этом это сообщение о
  конце СКАНИРОВАНИЯ, а не о конце загрузок, и числа `downloaded`/`failed` туда не попадают — они есть
  только в SW (`downloadStats`) и уходят лишь в окно прогресса.
  → На финале сессии SW отправляет в вкладку-инициатора одну сводку
  `{downloaded, failed, quarantined, hosts[], canRetry}` — и она живёт на странице до ухода
  с вкладки (не 5 с).
- **R9 (кнопка на странице).** В этой же строке — «Retry not-downloaded (N)»: то же массовое действие,
  без попапа. После ухода с вкладки остаются бейдж и попап.
- **R10 (бейдж, и без конфликта).** Чтобы увидеть «есть остаток» после навигации — бейдж на иконке.
  **Конфликт:** сегодня бейджем владеет upstream-`updateBadge` (`service.js:1109`): 'X' для
  заблокированных grants, иначе `''`, и он срабатывает на каждом `tabs.onUpdated` — то есть затре́т
  наш счётчик при любом обновлении вкладки. → Бейдж остаётся **у одного владельца**: `updateBadge`
  перерисовывается с учётом остатка (число/«!» + свой цвет), а не борется с ним.
- **R11 (персистентность обязательна).** Попап и бейдж читают **сохранённое** состояние остатка
  (R6), а не память SW: иначе через минуту после смерти воркера кнопки нет, а бейдж есть.

**Гейт:** `repro-bulk-retry` — (a0) сводка доходит до вкладки-инициатора и содержит `downloaded`/`failed`/`canRetry`;
бейдж перерисовывается после `tabs.onUpdated` с остатком (мутация «бейдж затёрт») и попап читает
персистентный остаток после «перезапуска воркера»; (a) N `failed`-строк ⇒ ровно N постановок в фильтр-очередь, один
подъём сессии, каждая строка входит со своей цепочкой; (b) `superseded` и фильтр-скипы не берутся
(мутация — дубликаты на диске); (c) карантинный хост идёт в медленном режиме, первый отказ ⇒ стоп,
сводка верна; (d) при остатке снимок сохраняется, восстановление не шлёт `resumeGroupAnalysis`,
после успешного retry — сбрасывается; (e) попап показывает кнопку только при `N>0`.
Плюс локи в `md-unit-smoke` (оба дерева).

## C. Новая задача при живых загрузках (вопрос 1 из `Errors.txt`)

**Что происходит сегодня (Ф10).** `handleOpenDownloadProgress` → `resetMassDownloadSession()`
удаляет все незавершённые строки и чистит обе очереди. Идущие `chrome.downloads` отменить
нельзя: они досчитаются, их `onChanged` снова создаст строку в **новой** сессии и увеличит
**новый** `downloadStats.downloaded`. Готовые к старту задачи из `downloadQueue` исчезают
без следа — пользователь не узнает, что часть уже найденного не скачалась.

**Решение (минимальное и честное):**

- **C1.** В `resetMassDownloadSession()` перед очисткой: каждая незавершённая строка
  (`pending`/`downloading`/`filtering`/любая не `completed`/`skipped`/`canceled`) переводится в
  `canceled` с причиной `'Superseded by a new scan — press Retry to download it in this session'`;
  то же для задач из `filterQueue`/`downloadQueue` (ровно как делает `handleStopScanning`).
  Идущие `chrome.downloads` **не** отменяем.
- **C2.** Осознанная цена, фиксируем в доке: завершение «старой» загрузки в новой сессии даст
  +1 к `downloaded` новой сессии (строка при этом станет `completed` — это правильно и видно);
  `checkAllQueuesEmpty` не объявит завершение сессии, пока такая загрузка жива (это корректно).

**Гейт:** расширение `repro-session-snapshot` (там уже есть сценарии снапшота и сессий):
новый кейс «reset при живой загрузке» — строка `canceled` + Retry, счётчики не уходят в минус,
`activeDownloads` не обнуляется (инвариант N-19), `downloaded` новой сессии учитывает завершение.

## D. Одиночное сохранение pixiv (Ф6–Ф9)

**Диагноз:**
- **D1 [оба дерева].** `case "download"` → `download(msg, sender.tab, sendResponse)` (как в
  upstream). Восстанавливает `params.incognito` на Firefox (приватное окно) и `msg.tabId`.
  Это подтверждённый нами дефект (Ф9), независимый от pixiv.
- **D2 [Chrome-only].** Падение «Download failed: Failed to fetch» — это CORS: путь
  `alterDownload` тянет байты `fetch`'ем из контента, а кросс-доменный `i.pximg.net` не отдаёт
  CORS-заголовки, поэтому промис реджектится всегда, независимо от Referer и CSP (Ф6, Ф7).
  Механизм, который в этом проекте уже доказанно работает — offscreen-документ (Ф8).
  Правка: в `case "download"` и в interrupt-хуке `chrome.downloads.onChanged`
  (там, где сейчас заказывается `alterDownload` у контента) сначала
  `await mdDnrEnsureRule(msg.url, msg.referer)`; если `mdDnrRuleActiveFor(...)` не `null` и
  `mdOffscreenSupported()` — тянуть байты offscreen-документом и отдать в `chrome.downloads`
  его object URL. Иначе — сегодняшний путь (без изменений).
  **Важно:** `mdTryOffscreenDownload` как есть звать нельзя — он пишет строки в
  `downloadProgress` и увеличивает `downloadStats.skipped` (это часть mass-download-сессии).
  Нужен тонкий вариант «fetch+download без учёта прогресса», общий код — вынести в параметр.
- **D3 [FF-only].** Отдельной правки не требуется: в FF-дереве `download()` уже передаёт
  `headers: [{name:'Referer', …}]` (FF 70+), и это документированная дельта.
- **Честно:** я **не** утверждаю, что «у upstream это работает, а у нас сломано» — в upstream тот
  же CORS-путь. После D2 нужен живой тест: сохранение картинки pixiv с попапа и хоткеем
  `[НУЖНА ЖИВАЯ ПРОВЕРКА]`.

**Гейт:** `repro-offscreen-single-save` — SW-путь `case "download"` с заглушками
`chrome.downloads/declarativeNetRequest`: (a) DNR-правило активно ⇒ один offscreen-fetch, строк
прогресса **нет**, `downloadStats` не меняется; (b) правило не активно ⇒ старый путь;
(c) ошибка offscreen ⇒ возврат к старому пути, `sendResponse` не теряется;
(d) `tab.incognito` доходит до `params.incognito`.

### Найденные дефекты самого замера (2 подтверждённых + 2 потери)

**Ф18. `timeouts=272` при `walk=218.9 s` и `unresolved=255` — счётчик ложный (доказано).**
Два независимых доказательства прямо из лога: (1) `272 × 8 с = 2176 с` не влезает в обход длиной
218.9 с; (2) настоящий кап-таймаут тоже вызывает `onResolved(null)` и попадает в `unresolved`, значит
`timeouts > unresolved` недостижимо без «фантомных» инкрементов. **Корень** (найден в коде):
таймер капа взводился **после** `PVI.load(src)`. Если движок отвечает синхронно внутри `load`
(`PVI.set` / `PVI.show('R_…')`), `cleanup()` выполняется, когда `timeout` ещё `undefined` — снять
нечего, таймер взводится следом и живёт до конца капа. Валидный ответ он больше не портит
(`resolved`-гард), но **считает ожидание, которого не было**.

**Ф19. `prefiltered=0` в блоке при `prefiltered=222` в строке статистики того же лога.** Поле просто
никогда не заполнялось: `_sendScanDiagnostics` читал `covered`/`unresolved`/`groups` из живых
счётчиков, а `prefiltered` оставался тем, что поставил `_mdDiagInit` (0).

**Ф20. Половина воркера после перезапуска пустая** (`groups=- … after-scan tail=-`): половинка
страницы едет в снапшоте, а `mdScanPhases` — нет, поэтому у замеров, ради которых всё и делалось
(сессия через два воркера), пропадали именно те отрезки, которые считает воркер.

**Ф21. `session=118.7 s` при 411 с реального времени** — число верное, но не то, что читается:
`totalMs = drained − sessionStartTime`, а `sessionStartTime` при восстановлении переписывается на
старт нового воркера (иначе классификатор вкладки навсегда видит сессию «потерянной»).

| 2 | `d.prefiltered = PVI.downloadAllFiltered \|\| 0` (живой счётчик обхода, как соседние) | `content.js` → `_sendScanDiagnostics` |
| 3 | `scanPhases: mdSnapshotPhases()` в снапшоте + `mdRestorePhases(snap.scanPhases)` при восстановлении; белый список `[groups, groupsEnd, download, scanDone]` — **без `drained`**; пустой/битый объект фаз не затирает живые метки | `mass-download/service-core.js` (`mdBuildSnapshot`, `mdApplySnapshot`, два новых хелпера) |
| 4 | `resumed: !!mdRecoveredInfo` в отчёте + `const restarted = sw.resumed === true` и строка-пояснение в блоке | `service-core.js` (`mdScanPhaseReport`), `options/download-progress.js` (`mdScanDiagLines`) |

**Что стало хуже / цена:** снапшот вырос на один маленький объект (4 числа); в тексте блока у
сессии через два воркера на две строки больше; таймер капа теперь взводится на несколько
микросекунд раньше (разница — длительность синхронного `PVI.load`). Планирование, очереди,
параллелизм и сам обход не тронуты. Пункт 3 меняет **только** читаемость отчёта — метки фаз
нигде не влияют на решения.

**Что теперь можно решить (P6).** Следующий лог даст честные числа: `timeouts` (полные ожидания
капа `da.resolutionTimeout`) против `unresolved` (правило не найдено) против сетевых отказов
хоста, и всё это — включая прогоны через перезапуск воркера. Инвариант для чтения:
**`timeouts ≤ unresolved` обязателен** (реальный кап-таймаут — подмножество `unresolved`).

**Проверка:** новый исполняемый харнесс
`.unlazy/review-verify-2026-09-12/repro-walk-timeouts.mjs` — **20/20 ×2 дерева** (реальный
`processNextInQueue` на виртуальных часах: 20 «быстрых» элементов не дают ни одного
`timeout` и не оставляют живых таймеров; реально зависший элемент считается ровно один раз и
попадает в `unresolved`). Харнесс **падал на коде до правки** ровно тем же образом, что и живой лог
(`pending=20`, затем `timeouts=20 unresolved=0`), — это и есть доказательство Ф18.
`repro-scan-diagnostics` **110/110 ×2** (включая дрейф `prefiltered`, round-trip фазовых меток,
случай «восстановились метки gen 1 → отчёт gen 2 не пустой», восстановление из мусора);
`repro-session-snapshot` **52/52** (`scanPhases` в снапшоте и у принявшего воркера, `drained` не едет);
`md-unit-smoke` — новые текстовые локи **и исполняемые** (реальные `mdSnapshotPhases`/
`mdRestorePhases` из обоих деревьев запускаются прямо в версионированном тесте, поэтому
инвариант не зависит от игнорируемой папки `.unlazy/`); `mutation-check` — **9 новых мутаций
кусаются** (в т.ч. «кап взведён после `load`», «`drained` просочился в белый список»,
«пустой объект фаз затирает живые метки», «нота о перезапуске по `gen > 1`»). Полный набор
верификаторов зелёный.
