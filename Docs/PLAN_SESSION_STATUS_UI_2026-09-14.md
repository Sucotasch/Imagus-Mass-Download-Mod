## Реализация (2026-09-14)

Сделано по плану, плюс четыре вещи, которых в плане не было и которые нашлись при проверке кода:

| # | Что | Почему появилось |
|---|---|---|
| 1 | `mdSessionConfirmShown` — показ вопроса владеет панелью | без этого следующий тик опроса затирал вопрос вместе с кнопкой через секунду |
| 2 | Ветка `none` = «Waiting for the background worker…», **не** остановка опроса | только что рождённый воркер отвечает `none` первые ~400 мс — `mdRestoreSession` работает на `setTimeout(…, 400)`; объявлять сессию мёртвой нельзя |
| 3 | `outcomes` и `current` в компактном ответе | без реестра панель не показала бы живые `failed`, без имени файла — ответ «сейчас грузится вот это» |
| 4 | Вкладка восстанавливает сводку и при refresh (терминальные фазы `getDownloadStatus` тоже несут `summary`) | иначе итоги жили только до перезагрузки вкладки |

Отклонения от плана по объёму — только в SW: реестр исходов (`mdSessionOutcomes`/`mdOutcomeByUrl`/`mdNoteOutcome`/`mdResetOutcomes`/`mdOutcomeCount`) добавился потому, что `downloadStats` не содержит `failed`, а выводить failed из усечённой таблицы — ровно тот дефект, который весь батч и убирает. Реестр — сессионный, ограничен размером страницы (как дедуп-множества) и едет в снимке.

Вне скоупа — как и было решено: охота за убийцей воркера, tail-панель для галерейной «Save», ETA. Строки панели остаются английскими (как и существующая плашка; у этого элемента локалей не было и раньше), значения для пользователя дают счётчики, а не текст.

Гейты: `md-unit-smoke` (блок **SESSION STATUS**: исполняются `mdSessionPhase`, `mdNoteOutcome`, строители панели и `mdSessionSummaryText`; лочится проводка и копия-не-форк), `mutation-check` **105/105** (16 новых), `md-marker-check`, `md-ff-delta`, все `scripts/verify-*.mjs`.

## Решения пользователя (2026-09-14)

1. **Финальная сводка** — на вкладке прогресса, держится до старта новой сессии (навсегда, не на 5 секунд).
2. **Новая задача во время активной сессии** — подтверждение-диалог на панели (одна кнопка).
3. **ETA** — только счётчики, никаких оценок скорости.
4. **Плашка на странице-источнике** — главный пользовательский индикатор, живёт весь хвост. Вкладка прогресса — инструмент разработки (пользователи её отключают).

## Проблема (подтверждено логом 2026-09-14 07:35)

- After-scan tail = 319.4 с загрузок **без единого признака на экране**: панель исчезает через 5 с после конца скана (`_stopKeepAwake` в content.js), вкладка прогресса по умолчанию отключена.
- Пользователь не может ответить: идут ли ещё загрузки, произойдёт ли перезапуск, сколько осталось, можно ли закрыть вкладку / начать новую задачу.
- `allDownloadsComplete` приходит на вкладку прогресса **без цифр** — «All downloads completed» на 5 секунд.
- Новый хоткей во время хвоста молча сбрасывает очередь: `handleOpenDownloadProgress` → `resetMassDownloadSession()` (non-terminal строки + активные прерываются, без единого слова).

## Архитектурное решение

**Панель-опрос** вместо второго push-канала SW→страница:

- После конца сканирования content начинает опрос SW раз в секунду: `getDownloadStatus({compact:true})` (без items).
- Панель рендерит строку из ответа: счётчики + «вкладку можно закрыть: да/нет» + баннер перезапуска (по смене `worker` / Recovered-флагу) + терминальное состояние (done/canceled → зелёная/серая сводка, опрос останавливается).

Почему опрос:
- Работает **через перезапуск воркера**: каждый опрос будит нового воркера и приносит Recovered-данные (панель не теряется при смерти фона).
- Не требует правок канала push (я один канал для вкладки прогресса, он точечный).
- Самоумирает вместе с вкладкой; 1 лёгкое сообщение/с — пренебрежимо.

**Побочное следствие (честно, замерено, а не обещано):** опрос = событие воркеру каждую секунду → во время хвоста воркер не может умереть от idle, а все наши abrupt-смерти замерены как раз между событиями (GEN-3: активность 1с до смерти; снимок: 0 in-flight). Вероятно, смерти во время хвоста прекратятся. GEN-замеры остаются на месте и покажут, так ли это. Это не цель, но совместимо с выводом «смерти безвредны» — отдельные правки keep-alive НЕ вносятся.

## Изменения по файлам

### 1. SW — `mass-download/service-core.js` (оба дерева)

- **a. `getDownloadStatus` компактный режим.** `msg.compact: true` → пропустить `items`. Добавить `phase`:
  `'none' | 'scan' | 'tail' | 'done' | 'canceled'` (чистая `mdSessionPhase()`):
  - `userCanceled` → `'canceled'`
  - `scanInProgress && !contentScanDone` → `'scan'`
  - `contentScanDone && (очереди непусты \|\| полёт > 0)` → `'tail'`
  - `contentScanDone && всё дренировано` → `'done'`
  - иначе `'none'`
  В `'done'`/`'canceled'` ответ несёт `summary` (stats + elapsed = now − sessionStartTime).
- **b. `allDownloadsComplete` несёт цифры.** Сообщение на вкладку прогресса дополняется `summary` (stats + elapsed), чтобы вкладка рендерила постоянную сводку.

### 2. Content — `content/content.js` (оба дерева + синхронизация `mass-download/content-block.js`)

Новый код — только внутри marker-секций (MASS-DOWNLOAD-*), чтобы `md-marker-check` держал byte-sync.

- **a. Панель живёт весь хвост.** В конце скана не удалять панель через 5 с: `_stopKeepAwake(finalMessage)` вызывается, но элемент при `phase='tail'` остаётся; копирайт-строка меняется на честную фазу.
- **b. Опрос `mdPollSessionStatus()`.** Старт: по `done:true` (после групп или напрямую). Каждые ~1000 мс: `chrome.runtime.sendMessage({cmd:'getDownloadStatus', compact:true})` → рендер. Строка:
  `Downloading 34 of 185 · 3 active · 12 queued · Tab safe to close: no` — счётчики только (решение 3), «осталось» = queued + active.
  Баннер перезапуска: при смене `worker` (gen) в ответе — строка `Background restarted HH:MM:SS — session recovered, nothing lost` (одноразово на перезапуск).
- **c. Терминальные состояния.** `phase:'done'` → зелёная сводка `Done: downloaded 185 · failed 11 · skipped 81 · 3m 42s`, fade через ~10 с, опрос стоп. `phase:'canceled'` → серая `Cancelled: 34 downloaded`, опрос стоп (заменит пустой текст текущего cancel-пути).
- **d. Подтверждение новой задачи.** В хоткее (line ~3538) и в `onMessage 'downloadAll'` (popup): перед `PVI.downloadAll` — `getDownloadStatus({compact:true})`; если `phase` = scan/tail → на панели кнопки: `[Start over — N still queued will be canceled]` / `[Cancel]`. Да → `PVI.downloadAll` как сегодня (reset сессии, скачанное сохраняется по `resetMassDownloadSession`). Нет → ничего. Если сессии нет — старт без диалога. Guard от повторного входа (`mdConfirmShown`).
- **e. Копирайт предупреждения по фазе.** Скан: «не покидайте страницу до конца сканирования» (как сегодня). Хвост: честная строка «вкладку можно закрыть: да/нет» (нет — когда queued>0 или retries>0, т.к. referer-ретраи идут через страницу; да — когда всё пусто и в полёте = 0).

### 3. Вкладка прогресса — `options/download-progress.js/html` (оба дерева)

- **a.** `allDownloadsComplete` с `summary` → постоянный блок «Готово: скачано N · ошибок M · пропущено K · время T» (до старта новой сессии, как решил пользователь). Остальной рендер вкладки не трогаем (это наш dev-инструмент).

## Последствия и защита (риск-чек)

### Перформанс: подтверждённые границы (проверено в коде 2026-09-14)

| Структура | Граница |
|---|---|
| Таблица строк `downloadProgress` | **≤ maxProgressRecords (100)** — `mdEvictOldestRows` вызывается на каждом апдейте |
| Очереди `filterQueue`/`downloadQueue` | ограничены размером страницы, дренируются в 0 |
| Дедуп-множества (`globalProcessedUrls`/хеши) | растут на каждый уникальный файл — **ограничены размером страницы, не временем**; чистятся на старте сессии |
| Снапшот `storage.session` | `MD_SNAPSHOT_DEBOUNCE_MS=1000` + guard на таймере → ≤1–2 записи/с; внутри ≤100 строк, ≤1500 задач ×2, ≤4000 ключей ×2 |
| Реестр in-flight запросов | ≤ `MD_INFLIGHT_MAX` (8) |

Стоимость опроса: компактный ответ ~200–300 байт, 1/с. **Компактный режим обязателен**: без него `getDownloadStatus` вызывает `serializeAllProgress()` (сериализация всех ~100 строк) на каждый вызов — разница ~250× (≈50 КБ/с против ≈200 байт/с мусора). Опрос не добавляет ни одной persistent-структуры; после `done`/`canceled` останавливается, постоянного keep-alive нет.

### Backoff опроса (защита от «бесконтрольного» расхода)

- 30 тиков подряд **без изменения** (phase + counters) → интервал 1 с → 3 с.
- Прогресс вернулся → интервал обратно 1 с.
- 5 минут без единого изменения → опрос останавливается, панель показывает строку «no progress for 5 min».

| Риск | Оценка | Защита |
|---|---|---|
| Трафик опроса | 1 лёгкое сообщение/с (без items) ~60/мин — пренебрежимо | компактный режим + backoff (см. выше) |
| Опрос будит воркер | Во время хвоста — это и нужно; после done/canceled опрос останавливается → воркер спит как раньше | фаза в ответе |
| Вкладка закрыта/выгружена | Опрос умирает с ней, на загрузки SW не влияет (загрузки не зависят от страницы, кроме referer-ретраев — им вкладка и не нужна: ретраи через content инициатора; при закрытой вкладке их просто не будет — счётчик «можно закрыть» это учитывает) | fire-and-forget |
| Гонка старт-подтверждение | Между «Да» и отправкой openDownloadProgress ничего не вмешивается; reset как сегодня | `mdConfirmShown` |
| Попадание в marker-секции | Всё новое — внутри MASS-DOWNLOAD-секций; иначе маркер-чек сломается | `md-marker-check` |
| Два дерева | service-core.js, content.js, download-progress.js × 2 + content-block.js | `md-ff-delta` + лок |
| Регрессия существующих локов | Новые функции чистые (`mdSessionPhase`, статус-рендер панели) — исполняемые локи | `md-unit-smoke`, mutation-check |
