## 2. Факты из кода и данных

**Какая ветка обхода какую паузу ставит** (`src-mv3-overlay/content/content.js`, функция
`processNextInQueue`; в этом же файле — всё, что ниже):

| Ветка | Условие | Пауза перед следующим элементом | Счётчик диагностики |
|---|---|---|---|
| Группа кандидатов | `Array.isArray(result) && result.length > 1` → `PVI.ambiguousUrlGroups.push(...)` | **100 мс** | `diag.groups = PVI.ambiguousUrlGroups.length` |
| Найден один URL | ветка `PVI.downloadAllFound++` → `downloadMass` | **150 мс** | **счётчика в блоке диагностики НЕТ** |
| Альбом | `Array.isArray(albumList) && albumList.length > 1` | **150 мс** | `diag.albums++` |
| Результата нет (`null`/`false`) | `PVI.downloadAllUnresolved++` | **10 мс** | `diag.unresolved = PVI.downloadAllUnresolved` |
| URL не строка / пустой | `PVI.downloadAllUnresolved++` | **10 мс** | тот же `unresolved` |
| `covered` (вложенное в контейнер) | `downloadAllCoveredElements.has(el)` | **10 мс** | `diag.covered = PVI.downloadAllCoveredCount` |
| Пустой дренаж / дубль / ошибка в `catch` | хвостовой `setTimeout(..., 10)` после `try` | **10 мс** | не считается |

**Прочие факты по коду:**

* Обход **строго последовательный**: следующий элемент запускается только из
  `setTimeout(PVI.processNextInQueue, N)` после завершения предыдущего. Параллельности в обходе нет.
* **Разрешение адреса идёт в ВОРКЕРЕ, а не в странице.** `PVI.find` возвращает либо готовую строку,
  либо объект с `URL`/`params`, и только для второго случая `PVI.load` → `PVI.resolve` отправляет
  запрос в воркер (`Port.send({cmd:'resolve', ...})`). При этом `PVI.load` со СТРОКОЙ не идёт в
  `resolve` вообще (условие `src === null || (src && src.params) || src === false`) — такая строка сразу
  отображается. **[ФАКТ]** Отдельно: `PVI.find` сам вызывает `resolve` в ветке правила
  `!rule.to && rule.res && rule.url` (`ret = URL.replace(rule.img, rule.url); ret = PVI.resolve(...)`), то
  есть «строка из `img`-правила» раунда не платит только если правило попало в другую ветку.
* **Перед отправкой запроса стоит НАМЕРЕННАЯ задержка:**
  `setTimeout(..., PVI.resolve_delay || (nowait ? 50 : Math.max(50, cfg.hz.delay)))`. Значения:
  `cfg.hz.delay = 300` (по умолчанию в `data/defaults.json`), т.е. при `nowait = false` — **300 мс**
  ожидания перед каждым запросом разрешения; при `nowait = true` — 50 мс. Переменная
  `PVI.resolve_delay` живёт между прогонами: путь предзагрузки выставляет её в `200`, а по завершении —
  в `0`, поэтому фактическое значение зависит от того, что выполнялось в странице раньше.
* **Параллельность разрешений ограничена самой страницей:** пока идёт обход, в воркер уходит ровно
  ОДИН запрос `resolve` за раз (следующий элемент не начинается, пока не пришёл ответ), тогда как
  воркер умеет валидировать `da.maxConcurrentFilters = 5` параллельно.
* Префильтр идёт блоками по **100** элементов с `setTimeout(processChunk, 50)` между блоками
  (895 элементов → 9 блоков → ≤8 пауз по 50 мс = ≤0.4 с; они внутри измеренной фазы `prefilter=0.7 s`).
* Плашка статуса обновляется каждые **20** элементов (`itemsScanned % 20`) — это только отображение,
  задержкой не является.
* Настройки по умолчанию: `da.maxConcurrentDownloads=3`, `da.resolutionTimeout=8`, `da.minImageSize=45`.
* Правила сайта в `data/sieve.json` для `rule34.xxx` (запись `Rule34.xxx-x-q-p`): есть `img`-правило
  (переписывание адреса превью в оригинал, без сети) и `link`-правило; скрипт `res` (731 символ)
  **содержит `XMLHttpRequest`** и вызывает его **синхронно** (нет `async = true`), то есть на элементах,
  которые разрешаются через `res`, поток страницы блокируется до конца запроса.
* Смежные записи того же сайта (`Rule34gen|Rule34Video|Rule34-videos-x-q-p`) тоже содержат
  синхронный `XMLHttpRequest`; `Rule34.Paheal-x-p`, `Rule34.us-x-p`, `Rule34Dev` — нет.

## 4. Знаменатель: `walk=171.9 s` — это ВЕРХНЯЯ граница самого обхода

**[ФАКТ] по коду:** на пути с группами (а он в этом логе и есть — `end=groups-analyzed`) `tWalkMs`
проставляется **внутри `handleGroupAnalysisComplete`**, то есть в момент прихода сообщения «анализ
групп завершён» — уже ПОСЛЕ того, как воркер разобрал 402 группы. Поэтому в `171.9 s` входит и
ожидание этого анализа, а не только обход.

**[ФАКТ]** из лога: собственный прогон анализа групп в воркере — `groups=3.8 s`.

**[ОЦЕНКА — требует проверки]:** значит, сам обход короче: `171.9 − (3.8 + задержка сообщений)`.
Нижняя граница выигрыша от снятия пауз при этом только растёт, поэтому для долей берём
консервативный знаменатель `168.1 s` (= 171.9 − 3.8):

| Величина | Значение |
|---|---|
| Доля пауз в измеренном `171.9 s` | **25.4 … 26.7 %** |
| Доля пауз в консервативном `168.1 s` | **25.9 … 27.3 %** |
| Собственное время элементов | 171.9 − (43.59 … 45.97) = **125.9 … 128.3 с** |
| В среднем на элемент (741) | **170 … 173 мс** |

**[НАБЛЮДЕНИЕ — требует проверки]:** комментарий рядом с этим местом в коде утверждает обратное —
что время анализа групп в `tWalkMs` НЕ попадает. Код и комментарий противоречат друг другу; проверять
надо на следующем прогоне (сравнить `walk=` с моментом дренажа очереди). Пока это значит только одно:
цифру `walk=` нельзя читать как «чистое время обхода».

## 6. Варианты ускорения — с ценой, допущениями и тем, что надо проверить

Ниже — **не решения, а оценки**. Каждый вариант требует живой проверки; ни один не внедрён.

### A. Снять фиксированные паузы обхода (или перевести их на событие)

* Ожидаемый выигрыш: **43.6 … 46.0 с** из 171.9 с, то есть **25 … 27 %** обхода. **[РАСЧЁТ]** по §3, §4.
* Допущение, которое НЕ проверено: паузы — чистый простой. В коде рядом написано, почему они есть:
  у движка общие `PVI.TRG`/`PVI.stack` и таймер разрешения, и запуск следующего элемента слишком рано
  позволяет отложенному ответу предыдущего «попасть» в новый захват. **Пока это не проверено живым
  прогоном на сайте со сложным правилом (rule34), выигрыш считать гарантированным нельзя.**
* Что проверять: на одном и том же листинге сравнить набор найденных URL и число `unresolved` до и
  после — при снятии пауз `unresolved` не должен вырасти, а `groups` не должен «поехать».

### B. Снизить паузу ветки «группа» (100 мс), не убирая остальные

* Ожидаемый выигрыш при 100 → 20 мс: `402 × 80 мс = 32.2 с`. **[РАСЧЁТ]** (при тех же допущениях, что в A).
* Плюс: меньшее вмешательство, чем полное снятие. Минус: те же риски, что в A, просто слабее выраженные.

### C. Разобраться с 322 элементами, не давшими результата (43 % от 741)

* **[ФАКТ]:** они лежат внутри 125.9 … 128.3 с собственного времени.
* **[ОЦЕНКА — требует проверки]:** при равномерном среднем (170 … 173 мс) их доля ≈ **55 с**. Это
  именно оценка: распределение по элементам в этом логе не измерено.
* **[ФАКТ]:** у сайта есть `res`-правило с **синхронным** `XMLHttpRequest` (§2) — на таких элементах
  поток страницы блокируется. **Связать эти 322 с `res` по этому логу НЕЛЬЗЯ** — привязки «элемент →
  правило» в логе нет. Это гипотеза для проверки, не вывод.
* Что проверять: сколько из 322 разрешались бы бесплатным `img`-правилом (превью → оригинал) и почему
  до него не доходит; сколько времени стоит один `res`-элемент на живом сайте.

### C-2. Задержка разрешения и последовательность разрешений — **потенциально самый крупный рычаг, но НЕ измерен**

* **[ФАКТ]:** перед каждым запросом разрешения стоит `Math.max(50, cfg.hz.delay)` = **300 мс** при
  `cfg.hz.delay = 300` и `nowait = false`; при `nowait = true` — 50 мс (см. §2).
* **[ОЦЕНКА — требует проверки] Границы, если бы эта задержка платилась за каждый элемент 741:**
  `741 × 50 мс = 37 с`, `741 × 300 мс = 222 с`. Верхняя граница **невозможна** (больше всего обхода
  171.9 с), значит либо фактическая задержка была 50 мс, либо значительная часть элементов вообще не
  шла через `resolve`. **Различить это по имеющемуся логу НЕЛЬЗЯ** — в нём нет ни признака «элемент
  разрешён в DOM / отправлен в воркер», ни длительностей по элементам.
* **[ОЦЕНКА — требует проверки]:** разумно ожидать, что ответ-массив (а их в этом прогоне 402)
  приходит из правила со скриптом `res`, т.е. через раунд до воркера. Но «пришло синхронно из `find`»
  этот лог отсечь не позволяет, поэтому считать, что все 402 платили задержку, — НЕЛЬЗЯ без замера.
  Искать надо ровно это: сколько элементов ушло в `Port.send({cmd:'resolve'})` и сколько времени
  прошло от вызова `resolve` до ответа.
* Что измерять первым: значение `nowait`/`resolve_delay` в момент прогона, число элементов, ушедших в
  `resolve`, и распределение времени на элемент. Это один замер в точке `PVI.resolve`.
* **[ФАКТ] Чего пока нельзя делать:** менять `hz.delay` «на глаз» — 300 мс это ещё и задержка
  наведения для обычного режима Imagus; правка затронет не только масс-загрузку.

### D. Загрузки: 373 с при `maxConcurrentDownloads=3`

* **[РАСЧЁТ]:** `373 s / 249 файлов = 1.50 с` на файл в среднем; при 3 параллельных это ≈4.5 с
  последовательной работы на файл. **[ФАКТ]** — длины файлов в логе есть (`3.76 MB`, `232.1 KB`, …),
  но длительностей нет, поэтому это среднее, а не распределение.
* **[ФАКТ]:** в логе массово встречается `403 … referer skipped: host pinned to browser download` —
  хост уже упирается в Referer-защиту. Поэтому надежды на простое поднятие потолка не подкреплены.
* Что проверять: поднять потолок на одном прогоне и сравнить число `403`/`SERVER_BAD_CONTENT` и итог
  по времени — без этого менять смысла нет.

### E. Хвост 225.8 с после закрытия плашки

* **[ФАКТ]:** это окно от закрытия плашки до последней загрузки, и оно **внутри** `downloads=373 s`
  (не суммируется с ним). Пользователь в это время видит «готово».
* Это вопрос **видимости**, а не скорости: счётчик «скачано X из Y» в хвосте меняет восприятие, но не
  длительность. Отдельно от A–D.

## 7. Почему этих измерений нет в логе

**[ФАКТ]:** телеметрия стоимости обхода (`_mdWalkPerfNew`/`_mdWalkBook`/`_mdWalkBucket`, `scanId`,
белый список `mdScanWalkForLog`, блок `walk cost (scan sN)` в Save Log) была внесена коммитом
`5918995` и **откачена** тем же днём: на этой сборке (2026.9.21.3) скан перестал запускаться, после
отката на `a01ec9b` (2026.9.21.2) — работает. Разбор и правила повторного захода (не трогать
планировщик обхода, вносить по одному шагу, после каждого — живой прогон) записаны в
`Docs/FIX_PLAN_REVIEW_2026-09-12.md` §PERF-1.

Поэтому §5 не «недостаток аккуратности», а прямое следствие: измеритель убран, и до его аккуратного
повторного внедрения распределение времени по элементам недоступно.

## 8. Наблюдения для отдельной проверки (не про задержки)

1. **[НАБЛЮДЕНИЕ — требует проверки] Два разных счётчика расходятся.** `Stats` даёт `downloaded=249`,
   а реестр исходов сессии — `completed=131` (плюс `failed=23`, `skipped=8`, всего 162 записи).
   Счётчики по построению разные (живой счётчик против реестра по URL), но расхождение 249 против 131
   не объяснено и не проверено. Раньше на этом же месте уже была путаница, из-за которой цифры в
   плашке читались как «почти всё провалилось» (см. `REPORT_GALLERY_BATCH_2026-09-06.md`, §UNITS-1).
2. **[НАБЛЮДЕНИЕ — требует проверки] `walk=` включает ожидание анализа групп** (§4) — противоречит
   комментарию в коде. Влияет только на чтение лога.
3. **[ФАКТ] Настройки по умолчанию `showProgressTab: true`** — страница прогресса открывается
   автоматически; её таблица ограничена `da.maxProgressRecords=100`, поэтому «на экране мало строк» —
   это потолок отображения, а не итог прогона.
