# План: доставка находок «страница → воркер» (2026-09-14)

Статус: **S1 внедрено, S6 внедрено, S2–S5 ждут решения владельца.**
Ветка: `feature/post-96-hardening`. Ветки-деревья: `src-mv3-overlay/`, `src-mv3-overlay-firefox/`.

## 0. Исходный вопрос

Живой прогон 2026-09-13 21:09: страница нашла больше 180 пунктов, воркер принял 8, вкладка
прогресса объявила «всё скачано». Формулировка владельца: «мы получили всё, что нужно, а потом
просто потеряли это? Может, хранить это лучше, вместо того чтобы перепроверять и перезапускать
уже отработавшие процессы?» — то есть предлагалось: страница пишет находки в `chrome.storage`,
воркер читает оттуда.

Перед внедрением это проверено по коду и документации. Один факт меняет весь план.

## 1. Проверенные факты

### F1. USER_SCRIPT-мир не имеет доступа к API расширения, кроме messaging

* MDN, `userScripts` (ред. 2026-09-03): «This isolation is similar to a content script
  environment, **except USER_SCRIPT worlds cannot access extension APIs**». Доступ к `runtime`
  включается отдельным флагом `configureWorld({ messaging: true })`.
* Chrome docs, `userScripts` → `WorldProperties`: из флагов, включающих API, существует **только**
  `messaging` («Specifies whether messaging APIs are exposed. The default is `false`»). Флага или
  настройки для `storage` нет; `storage.session.setAccessLevel()` адресует content scripts
  (ISOLATED), а не USER_SCRIPT-мир.
* В самом коде это уже видно:
  * `manifest.json` **не содержит `content_scripts`** — весь код страницы (`content/content.js`,
    `common/app.js`) зарегистрирован как user scripts (`background/service.js:914-945`,
    `world: "USER_SCRIPT"`);
  * `common/app.js` читает настройки не из storage, а через `Port.send({ cmd: "cfg_get" })`
    (`app.js:133`);
  * ни один файл контентной части (`content/`, `common/`) не обращается к `chrome.storage` —
    storage есть только в воркере (`mass-download/service-core.js`, `background/service.js`).

**Вывод: страница физически не может писать в `chrome.storage`.** Схема «очередь находок в
хранилище пишет страница» в текущей архитектуре нереализуема — не по сложности, а по отсутствию
самих API в этом мире.

### F2. Слушатель пользовательских сообщений регистрируется после `await`

`background/service.js:922`:

```js
async function registerContentScripts() {
    ...
    await chrome.userScripts.configureWorld({ csp: ..., messaging: true });
    await chrome.runtime.onUserScriptMessage?.addListener(onMessage);   // ← здесь
```

Единственный триггер на старте воркера — `updatePrefs(null, registerContentScripts)`
(`service.js:1149`), а `updatePrefs` до вызова колбэка ждёт `chrome.storage.local.get`. Для
контраста: `chrome.runtime.onMessage?.addListener(onMessage)` (`service.js:1196`) стоит на верхнем
уровне и срабатывает синхронно.

Сообщение из user script принимает **только** `onUserScriptMessage` — Chrome docs: «they're
received using dedicated event handlers (meaning, they don't use `onMessage` or `onConnect`)».

**Следствие: на каждом старте воркера существует окно, в котором расширение глухо к собственной
странице.** Всё, что страница отправит в это окно, теряется.

### F3. Страница не может узнать, что сообщение не дошло

`common/app.js:105-131`, `Port.send`: если `Port.listener` установлен — а он установлен
(`content.js:4785`/`4856`, `Port.listen(PVI.onMessage)`) — **всегда** берётся ветка с колбэком,
который читает и выбрасывает `chrome.runtime.lastError` (обёртка D-5: подавление шума «The message
port closed before a response was received» для fire-and-forget команд).

**Следствие:** `downloadMass`, `updateStatus`, `updateFilterStats`, `reportSkippedItem`,
`scanDiagnostics` — «выстрелил и забыл», без единого признака потери.

### F4. Нет подтверждения приёма (ACK)

`background/service.js:637-639`:

```js
case 'downloadMass':
    handleDownloadMass(msg, sender);   // sendResponse не передаётся и не вызывается
    break;
```

`handleDownloadMass` (`service-core.js:346`) только кладёт задачу в `filterQueue`. При этом
страница **до** отправки увеличивает `PVI.downloadAllFound` и добавляет дедуп-ключ
(`content.js:5274-5284`).

**Следствие:** страница считает пункт доставленным, воркер его мог не видеть, сверить числа нечем.

### F5. Страница, закончившая обход, отвечает воркеру «меня нет»

`content.js:4697`: `if (!PVI.downloadAllActive) return;` — после конца обхода `resumeGroupAnalysis`
игнорируется. Воркер читает тишину как осиротевший контент-скрипт и закрывает сессию:
`MD_RESUME_ANSWER_MS = 20000` (`service-core.js:570`), проверка в `mdProbeInitiatorTab`
(`:766-783`), тик — alarm `md-session-keepalive` с периодом 0.5 мин (`:1537-1560`). Отсюда 30.5 с
в логе 21:09 (20 с + первый тик).

**Следствие:** живая страница, у которой остались недоданные пункты, объявляется мёртвой ровно в
том случае, когда потеря уже произошла.

### F6. Поздняя досдача выбрасывается по замыслу

`handleDownloadMass` намеренно не оживляет сессию (Audit N-02, `service-core.js:346-352`): задачи,
пришедшие после `scanInProgress = false`, помечаются `canceled` в фазе фильтра.

**Следствие:** «просто послать ещё раз позже» само по себе не решение — **пока страница досдаёт,
сессия должна оставаться открытой.**

## 2. Что это значит для лога 21:09

| Наблюдение | Чем объясняется |
|---|---|
| `Recovered: 8 row(s)`, страница нашла ~180 | расхождение чисел нигде не сверяется: у страницы свой счётчик, у воркера свой (F4) |
| нет половины страницы в диагностике (`walk:`, `phases (content)` отсутствуют), `groups=-`, `after-scan tail=-` | ни одно сообщение страницы в это поколение не дошло — либо окно F2, либо остановка обхода |
| `session=30.5s` | `MD_RESUME_ANSWER_MS` (20 с) + первый тик alarm (F5) |
| вкладка прогресса сказала «всё скачано» | все строки, которые воркер успел принять, были терминальными |

**Чего лог 21:09 доказать не может:** почему страница замолчала. Два равноправных механизма —
окно F2 (сообщения уходят в пустоту) и остановка самого обхода (замороженная вкладка). Оба дают
одинаковый итог, и **нынешняя диагностика их различить не в состоянии — это дефект инструмента, а
не факт о мире.**

При этом по логу видно: прогон, где снапшот нашёлся (`Recovered: 8 row(s)`), означает, что
перезагрузки расширения не было — `chrome.storage.session` очищается при reload/update,
перезапуске браузера и не очищается при перезапуске воркера (Chrome docs, `storage`). То есть
контекст контент-скрипта оставался валидным, и версия «страница осиротела от обновления» снята.

## 3. Решение

Порядок выбран так, чтобы **сначала закрыть доказанный дефект и получить числа**, а тяжёлую
машинерию строить только на измеренном.

### S1 — слушатель регистрируется синхронно (внедрено)

`chrome.runtime.onUserScriptMessage?.addListener(onMessage)` перенесён на верхний уровень, рядом с
`onMessage`; поздняя регистрация внутри `registerContentScripts()` удалена (дублирующий
`addListener` одного и того же обработчика не нужен).

Затраты: ноль (перенос строки). Риски: регистрация до `configureWorld` безвредна — сам
`configureWorld` остаётся на месте, а конфигурация мира живёт в браузерном процессе и переживает
перезапуск воркера (иначе messaging не работал бы и сейчас — обычные прогоны доставляют сотни
пунктов).

### S6 — учёт реальных потерь доставки (внедрено)

`Port.send` продолжает глушить шум, но **классифицирует** `lastError`:

| `lastError` | Значит | Учёт |
|---|---|---|
| `Receiving end does not exist` | сообщение **не доставлено** | `failed++` |
| `Extension context invalidated` | расширение перезагрузили, доставки не было | `failed++` |
| `The message port closed before a response was received` | доставлено слушателю, который ничего не ответил (все mass-download команды fire-and-forget) | **не** потеря |

Счётчики (`sent`, `failed`, `lastError`) едут в лог: в payload `scanDiagnostics` **и** в каждый
`updateStatus` (чтобы последние числа выжили даже если потеряется именно последнее сообщение).
Печать — одна строка в блоке `Scan diagnostics`:

```
  page → worker: sent=182 not-delivered=175 (last: no-receiver)
```

`lastError` хранит **класс** (`no-receiver` / `context-gone`), а не текст Chrome: текст зависит от
версии и локали, а решение принимается по классу. Воркер валидирует payload (только три ключа,
только числа, `failed ≤ sent`, `lastError` обрезан до 40 символов).

Это и есть инструмент, различающий F2 и остановку обхода: следующий прогон даёт
**прямой ответ**, был ли поток сообщений живым.

### S2–S5 — durable hand-off (жду решения владельца)

Предлагается, но **не внедрено**, потому что меняет контракт сообщений и жизненный цикл сессии:

* **S2.** `downloadMass` (и прочие fire-and-forget) отвечают **синхронным** `sendResponse({ok:true,
  seq})`. Синхронно — значит без `return true` и без удержания канала (см. готчу в AGENTS.md про
  blanket `return true`).
* **S3.** У страницы появляется **исходящая очередь** (`PVI.downloadAllOutbox`): пункт уходит из
  неё только после ACK; при неудаче — повтор с нарастающей паузой. Дедуп-контракт stage 4a
  (и восстановленные из снапшота ключи и терминальные строки) делают повтор идемпотентным: уже
  скачанное уходит в `Duplicate (same file)` — измерено в прогоне 20:33 (92 строки).
* **S4.** Страница отвечает на `resumeGroupAnalysis` не только пока идёт обход, но и **пока у неё
  есть недоданное** («жива, досдаю N»). Тогда окно 20 с/2 мин перестаёт закрывать живую сессию
  ровно в том случае, который теряет работу, и перестаёт быть «догадкой про 2 минуты» — условие
  становится фактом.
* **S5.** Честное окончание: `endedBy` (`page-silent` / `no-initiator` / `user-cancel` / `drained`)
  + числа («передано X из Y, не подтверждено Z»); вкладка прогресса вместо «всё скачано» говорит
  «завершено досрочно».

## 4. Последствия (проверено в комплексе)

**S1 + S6:**

* Производительность: `Port.send` — одна проверка `lastError` в колбэке (без записи в консоль);
  сообщений столько же.
* Потери функционала нет: подавление шума D-5 сохранено, поведение при штатной работе не меняется.
* Совместимость: новые поля в сообщениях аддитивны, воркер их игнорирует, если они не пришли
  (старая страница + новый воркер и наоборот работают).
* Firefox: те же два файла, `onUserScriptMessage` есть в обоих деревьях.

**S2–S5 (если делаем):**

* Стоимость: один ответ на сообщение (синхронный, без очередей); очередь ~180 объектов ≈ 20 КБ на
  странице; пересылка повторов только при реальных сбоях. Параллелизм фильтров/загрузок не
  затрагивается вообще.
* Риск двойной закачки снимается дедупом и восстановленными ключами — это уже работающий механизм.
* Риск «вечного ожидания» снимается тем, что условие ожидания — не время, а непустая очередь у
  живой страницы; доказанно мёртвая страница (вкладки нет, `tab.discarded`) закрывается сразу.
* Пропадает параметр `MD_RESUME_ANSWER_MS` как «точка потери» — он перестаёт быть догадкой.

## 5. Отклонённые варианты

| Вариант | Почему нет |
|---|---|
| Очередь находок в `chrome.storage` (исходное предложение) | **Нереализуемо**: у USER_SCRIPT-мира нет API расширения, кроме messaging (F1). Потребовало бы завести настоящий content script для передачи — другой способ инъекции; `PVI` IIFE-локален (готча AGENTS.md), значит нужен ещё и postMessage-мост. Цена велика, выигрыш перекрывается S2–S5 |
| Окно ожидания 2 минуты | Не добавляет надёжности, а удлиняет догадку: время не создаёт доставку |
| Журнал страницы в `localStorage`/`sessionStorage` | storage страницы общий с хостом — враждебная страница может читать и подделывать; всё равно умирает с вкладкой |
| Ничего не делать, положиться на кнопку Retry | Пользователь не знает, какие именно пункты потеряны (F4): нечего переспрашивать |

## 6. Гейты (внедрённая часть)

* `repro-handoff-delivery.mjs` (новый, S6): **56/56 ×2 дерева**. Реальный `Port.send` обоих
  деревьев в мире-заглушке с настраиваемым исходом — классификация трёх видов `lastError`,
  закрытый порт не считается потерей, выброс живого контекста не меняет поведение (промис
  по-прежнему отклоняется), D-5 сохранён (ответ доходит до слушателя), снапшот — копия;
  реальные `mdNormalizeSendStats`/`mdRecordSendStats` на враждебных payload'ах (`__proto__`,
  `NaN`, отрицательные, `failed > sent`, 200-символьный `lastError`); реальный `mdScanDiagLines`
  на числах 21:09 (`sent=182 not-delivered=172`).
* `tools/md-unit-smoke.mjs`: локи `D-5b` (классификация — **исполняемая**, а не по регулярке;
  счётчики реально инкрементируются; clamp и обрезка) и `D-5c` (ровно одна регистрация
  `onUserScriptMessage`, на верхнем уровне, без `await`).
* `mutation-check`: **8 новых мутаций HANDOFF, все кусаются** (в т.ч. возврат поздней регистрации
  слушателя и «закрытый порт = потеря»).
* `md-unit-smoke`: лок на порядок — `onUserScriptMessage` должен быть зарегистрирован **на верхнем
  уровне, до первого `await`** (это ровно та регрессия, которую S1 закрывает), и лок на форму
  `sendStats` в payload.
* `mutation-check`: мутация «слушатель снова внутри async-функции» и «closed-port считается
  потерей» обязаны ломать тест.
* Для S2–S5 (когда решим): расширение `repro-resume-after-restart` (очередь непуста → сессия
  остаётся; очередь пуста → закрывается; вкладки нет → закрывается сразу; после «Стоп» — **не**
  оживлять) + `repro-handoff-outbox` (ACK убирает ровно один пункт, повторный ACK — ничего,
  backoff ограничен, cap соблюдён, отмена сбрасывает очередь).
