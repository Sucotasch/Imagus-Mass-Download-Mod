## FIX-1 (P1, подтверждён исполнением) — BT-01: owner-гвард аккумулятора `PVI.res`

**Диагноз (гейты репро `G1–G3`).** `PVI.res_owner` пишется объектом `d.params.rule` в ветке
`{loop}` и сравнивается с `d.params.rule` следующего круга. Круг — это новое сообщение через
`chrome.runtime.sendMessage` (structured clone) / FF JSON-relay, т.е. новый объект. Сравнение
всегда `false` → аккумулятор мёртвой цепочки не очищается → «отравленный альбом» на E-Hentai `/g/`.

**Правка (2 строки × 2 дерева, `content/content.js`, ветка `resolved`):**

```js
//  string: owner is a RULE ID (d.params.rule.id === index in cfg.sieve), not an
//  object: every {loop} round arrives as a NEW structured clone, so object
//  identity can never match across rounds (that check was dead code).
if (PVI.res_owner === d.params.rule.id) { PVI.res = undefined; PVI.res_owner = undefined; }
...
PVI.res_owner = d.params.rule.id;
```

**Проверка последствий:**
- `d.params.rule.id` гарантированно есть в этой ветке — строка 4412 (`cfg.sieve[d.params.rule.id]`)
  читает его раньше try, значит «cannot read id of undefined» невозможен.
- `id` — числовой индекс правила в массиве `cfg.sieve`, стабильный на всех кругах (SW эхо-ит
  `params` без изменений, `background/service.js:466–471`).
- `PVI.res_owner` больше никто не читает (3 вхождения в файле) — смена типа безопасна.
- Поведение очистки не расширяется: очистка только в `catch`, только для правила-владельца
  (гейты `G5`/`G6`). Параллельная пагинация **другого** правила не затрагивается.
- Остаточный риск (был и до фикса, upstream-ограничение): две параллельные цепочки **одного**
  правила делят один `PVI.res`.
- `content-block.js` не меняется (участок вне маркеров, гейт `S1`).

**Гейты после правки:** репро `repro-bt01.mjs` (обоих деревьев) — `PASS`; новый лок в smoke
(сравнение по `.id` в обоих деревьях, отсутствие сравнения по объекту); `md-marker-check` 5/5×2.

## FIX-2 (P2) — NF-2: `_interruptHandled` отсутствует в Firefox

**Диагноз (`S4–S4e`).** В FF поиск задачи идёт до `chrome.downloads.search`, а ветка `interrupted`
(с `advanceToNextCandidate`) — внутри его async-колбэка. Две подряд пришедшие дельты (`state` +
`error`) обе проходят `if (!existingTask) return` и обе доходят до advance; `advanceToNextCandidate`
делит `_candidates` с исходной задачей → теряется кандидат и возможна вторая загрузка того же
элемента. Слот не течёт (`_slotReleased` идемпотентен).

**Правка (FF `mass-download/service-core.js`, ветка `interrupted`, зеркало Chrome):**

```js
const firstVerdict = !existingTask._interruptHandled;
existingTask._interruptHandled = true;
const interruptReason = 'interrupted: ' + (results[0].error || 'unknown');
if (alreadyCanceled || !firstVerdict) {
    releaseDownloadSlot(existingTask);
} else {
    if (!advanceToNextCandidate(existingTask, interruptReason)) { ...failed row... }
    releaseDownloadSlot(existingTask);
}
```

**Проверка последствий:** гвард ничего Chrome-специфичного не содержит (FF-ветка синхронная, без
offscreen); вторая дельта уходит в `releaseDownloadSlot` (идемпотентен), т.е. ровно поведение
Chrome. Ветка `complete` не трогается (двойной `complete`-дельты не наблюдаются, счётчик
`downloadStats.downloaded` не под угрозой). Новый лок в smoke: гвард есть в обоих деревьях.

## FIX-3 (P2, новая) — NF-7: offscreen idle-close обрывает идущий медленный fetch

**Диагноз (`O1–O7`, репро на настоящем `armIdleClose`).** `liveObjectUrls++` — после полного чтения
тела; `armIdleClose()` — только при `mdOffscreenFetch`/`mdOffscreenRevoke`. Тело, читаемое дольше
30 с, выглядит «простоем» → `window.close()` посреди запроса → `sendResponse` не приходит →
ретраи → `miss()` → падение на следующего кандидата (потеря оригинала до 32 MiB, тот самый
регресс, который закрывал лимит 32 MiB).

**Правка (offscreen.js, оба дерева — файлы обязаны остаться байт-идентичными):**
1. `inFlight`-счётчик: `inFlight++` в ветке `mdOffscreenFetch`, `inFlight--` в обоих продолжениях
   `fetchBlob(...)`; в `armIdleClose()` при `inFlight > 0` таймер **перевзводится** (документ не
   закрывается во время запроса) — по образцу существующей защиты живых blob.
2. **Stall-таймаут вместо общего:** `AbortController` + таймер, который перевзводится перед каждым
   `reader.read()` (и перед `fetch`). Так обрывается **зависшее** соединение (нет данных N с), а
   медленная, но идущая передача остаётся возможной — иначе 32 MiB на 100 КБ/с не пройдут.
   Таймаут делает `inFlight` конечным при любом сценарии, поэтому документ всё равно закрывается.
3. Обновить шапку файла (она сейчас утверждает, что закрытие не может задеть активную загрузку).

**Проверка последствий:**
- Никаких новых путей в SW: провал stall-таймаута идёт тем же `miss()` → `requeueNextCandidateForFilter`
  / `advanceToNextCandidate`, что и сегодняшний сетевой провал.
- Лимит 32 MiB и пре-чек `Content-Length` не меняются; память не растёт.
- Idle-close по-прежнему закрывает неиспользуемый документ; HARD_LIFETIME для живых blob не меняется.
- `AbortError` попадает в лог как причина (`Offscreen fetch failed: ...`), т.е. диагностика лучше.
- Значение stall-таймаута — 60 с (больше любого разумного межбайтового промежутка, меньше
  пользовательского «зависло»).

**Гейты:** репро `repro-offscreen-idle.mjs` переписывается на новые инварианты
(`inFlight>0 ⇒ нет закрытия`, `armStall` вызывается перед каждым `read`, `AbortController` есть);
smoke-лок на идентичность файлов + наличие `inFlight`/stall.

## FIX-4 (P3, новая — из `Errors.txt`) — NF-8: `Unchecked runtime.lastError: Download must be complete`

**Диагноз.** Источник — `mdRemoveFileThenErase` в ветке `SERVER_FAILED`. По Chromium IDL
(`chrome/common/extensions/api/downloads.webidl`): `removeFile` требует, чтобы элемент был
`complete`, иначе отдаёт ошибку через `runtime.lastError`; `erase` удаляет **только запись из
истории** («without deleting the downloaded file»). Прерванная загрузка (`SERVER_FAILED`) не
`complete` → `removeFile` **всегда** падает → колбэк не читает `lastError` → Chrome печатает
«Unchecked runtime.lastError». Это шум уборки; к обрыву загрузок отношения не имеет.

**Правка:**
- в ветке `SERVER_FAILED`: `removeFile` вызывать только если `results[0].state === 'complete'`,
  иначе — только `erase` (то, что и так делается дальше);
- в колбэках `removeFile`/`erase`/`cancel` читать `chrome.runtime.lastError` (диагностика в
  `console` на уровне debug), чтобы Chrome не писал «Unchecked»;
- переписать комментарии Fix D: причина отказа `removeFile` — не «нет файла», а «элемент не
  complete»; частичный файл прерванной загрузки через API удалить нельзя (ограничение платформы) —
  зафиксировать честно вместо ложного «Fix D удаляет партиал»;
- в `background/service.js` (Chrome, popup-save путь) — та же гигиена в двух колбэках.

**Проверка последствий:** поведение не меняется (erase выполнялся и выполнялся бы); исчезает
гарантированно падающий вызов; риск потери функциональности нулевой — если элемент `complete`,
`removeFile` по-прежнему вызывается. Локи: smoke — «нет колбэков downloads.* без чтения
`lastError`» в two trees' mass-download файлах.

## FIX-5 (P2, из `Errors.txt` 2026-09-12) — маркер воркера и детект потери состояния

**Диагноз (доказан данными, не гипотеза).** `log/Empty log …18-20-54.txt` имеет `Session start: -`,
`saved=0`, `total shown=0` при том, что вкладка показывала 406 найденных и 100 строк. `sessionStartTime`
пишется **только** в `handleOpenDownloadProgress()`, а строки в вкладке — это пуши SW, значит ответил
**новый** инстанс: сессия потеряна вместе со смертью воркера (очереди/статистика/прогресс — только в
памяти). Вкладка прогресса **push-only** (ни одного `setInterval`) ⇒ замирает навсегда; Save Log
поднимает свежий воркер ⇒ пустой лог; `chrome.alarms.onAlarm` при холодном старте видит пустые
счётчики (`sessionHasWork()` ложно) и удаляет alarm ⇒ след стирается. Подробно — `REPORT §30.7`.

**Правка (сделана):**
- `mass-download/service-core.js` (оба дерева): `workerStartMs`, история стартов `workerStarts` в
  `chrome.storage.session` (ключ `mdWorkerStarts`, хвост 24), `mdRecordWorkerStart()` при оценке скрипта
  (`console.info 'worker gen N started…'`), `workerMarker()`; `sessionStart` + `worker` в ответе
  `getDownloadStatus`; `sessionStart` в пушке `registerProgressTab`.
- `background/service.js` (оба дерева): `worker` в ответе `getDownloadLog`.
- `options/download-progress.js` (оба дерева, байт-идентичны): чистые `countNonTerminal()` и
  `classifyWorkerState(resp, rows, prevSessionStart)` → `'lost' | 'newsession' | 'ok'`; баннер
  `⚠ Background was restarted…` в существующем `#scanStatus` (без правки HTML);
  `setInterval(workerWatchdog, 5000)` — проба только при видимой вкладке, непустых нетерминальных
  строках и простое ≥20 с; в Save Log — `Worker: …` и блок `!! SESSION STATE LOST`.

**Проверка последствий.** `storage.session` уже используется (`cfg`-обёртка), ключ не конфликтует;
отсутствие API (или отказ) глушится `try/catch` + `.catch` — маркер остаётся в памяти. Проба — одно
сообщение на простой ≥20 с; при живой сессии она почти не идёт, а при мёртвой — поднимает воркер и
сразу получает ответ (`.catch`/`lastError` читаются). Ложный баннер возможен только если у страницы
есть нетерминальные строки и воркер сообщает `sessionStart === null`; случай «новая сессия на тех же
строках» отделён исходом `'newsession'` (сравнение с запомненным `sessionStart`), а пустой список
строк или все строки терминальные дают `'ok'`.

## FIX-6 (P2, из дампа `Errors.txt` 2026-09-12) — градиентный watchdog загрузки

**Диагноз.** Строки `Downloading` с размером `-` и `0%` — уже запущенные загрузки без единого
`onChanged`; каждая держала один из `maxConcurrentDownloads = 3` слотов до жёсткого
`WATCHDOG_MS = 5 мин`, поэтому при молчащем CDN (rule34 после сотен запросов) очередь стоит волнами по
5 минут. `filterTimeMs`/лог это подтверждают только косвенно — прямая улика в дампе страницы.

**Правка (сделана):** `const STALL_MS = 60 * 1000` и `armStallWatchdog(task, downloadId)` (оба дерева):
тишина ⇒ `failed 'No data from server (stalled)'` → `cancel` → `erase` → `releaseDownloadSlot`
(именно в таком порядке: релиз убирает `downloadIdToTask`, поэтому USER_CANCELED-интеррапт от этого
`cancel` не находит задачу и не может дать второй вердикт/advance). Вызов на арме — в колбэке
`chrome.downloads.download`, перевзвод — в голове `onChanged` (до асинхронного `downloads.search`),
снятие — в `releaseDownloadSlot`. Любая дельта перевзводит таймер ⇒ медленная, но живая передача
(включая потоки без `Content-Length`) не режется; жёсткие 5 минут остались как последняя сетка.

**Проверка последствий.** `armStallWatchdog` идемпотентен по таймеру; для уже освобождённой задачи
`onChanged` не перевзводит (`_stallTimer === null`); `releaseDownloadSlot` вызывается один раз благодаря
`_slotReleased`. Известный унаследованный край: если сессия сброшена при живых загрузках
(`resetMassDownloadSession` их не отменяет), таймер старой задачи сработает позже и обновит строку
старого URL — ровно как это делал и делает 5-минутный `WATCHDOG_MS`; регресса нет.

### D-5. Шум «Unchecked runtime.lastError: The message port closed…» (найдено 2026-09-12)
`Port.send` отдаёт `Port.listener` как **колбэк ответа** (`common/app.js:109`), а listener установлен
(`content/content.js:4668`), поэтому каждое неотвеченное сообщение (`downloadMass`, `updateStatus`,
`updateFilterStats`, `reportSkippedItem`, `resolveAndDownloadGroups`, `openDownloadProgress`, `referer*`,
`stopScanning`) даёт строку в консоли; `content.js` не читает `lastError` вообще. Это маскирует
настоящие ошибки в логе расширения. Правка: не подставлять `Port.listener` в `send`, а в самих
`send`-сайтах либо `await` с `.catch(()=>{})`, либо обрабатывать `lastError`. Отдельно: ответы,
попадающие в `PVI.onMessage` как команды (сейчас безвредно).

### D-6. fetlife — 403 из фильтр-фазы и `credentials` (найдено 2026-09-12)
Подтверждено кодом: фильтр-`fetch` из SW идёт **без `credentials`** ⇒ по правилам Fetch это
`same-origin` ⇒ для чужого хоста cookie не отправляются вообще. Любой host, отдающий файл только по
сессии, гарантированно получает 403 в фильтр-фазе. Кандидат: `credentials:'include'` на HEAD/GET и на
групповой валидации (host-permissions есть). Требует живой проверки на fetlife/e-hentai: меняет и
приватность, и ответы сервера.

### D-7. Пер-хост пейсинг + breaker по хосту (найдено 2026-09-12)
`urlValidationStats.circuitBreakerOpen` — **глобальный**: шторм 403 на rule34 на 30 с подавляет
валидацию и для остальных хостов сессии. Плюс арифметика шторма (8 кандидатов, 91/95 попыток — 403)
как вероятная причина бана на Avito. Кандидат: минимальная пауза между запросами к одному хосту +
эвристика перебора кандидатов без повторных полных загрузок.

### D-8. Устаревший `scripts/verify-security.mjs` (найдено 2026-09-12)
Падает на `firefox service must import mass-download`: ищет строку `mass-download/service-core.js` в FF

проверяется вообще. Обновить ассерт (или исключить FF из файла, оставив `md-ff-delta`).

### D-3. Avito — «забанило при пакетной загрузке» + галерея с видео не качает ничего
Требуется решение: (а) детектор лимитирования — считать подряд идущие `429/503` (и,
опционально, мгновенные 403) по хосту в фильтр-фазе; при пороге (5) — **один** видимый warning на
хост («сайт ограничивает запросы, уменьшите `maxConcurrentFilters`/`maxConcurrentDownloads`») и,
как опция, авто-пауза очереди по этому хосту на 30 с. Автоматически менять настройки

## FIX-7 — снапшот сессии в `chrome.storage.session` + восстановление

**Что сделано.** Пока `scanInProgress`, в `mdSessionSnapshot` зеркалится вся возобновляемая часть
сессии: строки таблицы (+ задача: `referer`, `source`, `isHd`, `elementInfo`, `contentType`,
`fileSize`, `filterMethod`, `httpStatus`, `filename`, цепочка кандидатов, цепочка попыток,
`candidateCount`, `pickReason`), `filterQueue`, `downloadQueue`, `downloadStats`, дедуп-наборы
(`globalProcessedUrls`, `globalProcessedMediaHashes`), обученные `refererHostModes`, `sessionId`,
`sessionStart`, id вкладки-инициатора. Запись — дебаунс 500 мс с защитой по таймеру (поток
прогресс-дельт даёт не более двух записей в секунду), плюс немедленный flush в
`chrome.runtime.onSuspend`.

Новый воркер через 400 мс после оценки скрипта (`setTimeout(mdRestoreSession, 400)`) читает снапшот и
восстанавливает сессию, если она была оборвана на ходу:

| Класс строки | Что делает восстановление | Почему так |
|---|---|---|
| `completed` / `failed` / `skipped` / `canceled` | возвращается как есть | это история, а не работа |
| `downloading` с `downloadId` | `chrome.downloads.search({id})`: `in_progress` — adopt (маппинг + свежий stall-watchdog + слот), `complete` — completed, иначе — следующий кандидат / failed | браузер продолжает загрузку после смерти воркера; повторный `download` дал бы файл «(1)» рядом с живым |
| `pending`/`scanning` (в т.ч. задачи из обеих очередей) | de-dup-ключи освобождаются и задача уходит **в фильтр-фазу** | единый путь: заново применяются size/type-фильтры; ключи снять обязательно, иначе `processFilterQueue` отбросит её как дубль |
| задача с `_objectUrl`/`_blob` | строка → `failed` + «Retry», задача не переставляется | байты лежат в объект-URL страницы/Blob воркера и через рестарт не переживают; повторный download по тому же URL дал бы 404 |

`sessionStartTime` переводится на текущий воркер: `classifyWorkerState` во вкладке сравнивает старт
воркера со стартом сессии, и без этого восстановленные строки навсегда читались бы как `lost`.

**Почему `storage.session`, а не `storage.local`.** Chrome очищает session-storage при завершении сессии
браузера и при перезагрузке/обновлении расширения (developer.chrome.com/docs/extensions/reference/api/storage) —
это ровно те два случая, когда сессия выброшена осознанно. Снапшот физически не может пережить свою
сессию браузера и не может воскресить сессию, которую владелец перезапустил руками; `onInstalled`
дополнительно удаляет его (страховка для Firefox, где session-storage живёт до закрытия браузера).

**Что отклонили и почему.**

- *Restore через повторный скан страницы* (просить контент-скрипт пересканировать DOM): требует всё
  равно персистить дедуп-набор, иначе уже скачанное скачается повторно; плюс повторный скан зависит от
  того, догрузилась ли страница, и плодит дубли через `conflictAction: uniquify`. Снапшот точнее и
  меньше по объёму.
- *Персистить сами Blob/object-URL*: невозможно технически (Blob не сериализуется в storage, `blob:`
  URL живёт в контексте-создателе).
- *Восстанавливать всё «как было» вместе с очередью браузера*: `chrome.downloads` — единственный
  источник правды о том, что реально происходит с файлом, поэтому adopt через `search({id})`, а не
  слепое переигрывание.
- *Уменьшить частоту/объём снапшота до только-очередей*: строки без задач теряют `filename`/`referer`/
  историю попыток, и Save Log после рестарта перестал бы быть доказательством.

## FIX-8 (вкладка) — мёртвая регистрация и «вечный pending» на экране

`workerWatchdog` в `options/download-progress.js` выходил по `if (stateLost) return;` — то есть после
первого баннера проба останавливалась **навсегда**. При этом регистрация вкладки в воркере умирала
вместе с воркером, а pushes идут только по `downloadProgressTabId`: восстановленная сессия не могла
достучаться до страницы (замкнутый круг: страница не узнаёт о новой сессии, потому что не спрашивает,
а воркер не может ответить без регистрации). Исправлено: проба продолжает идти (1 сообщение / 5 с) и
при вердикте `newsession` страница сама делает `registerProgressTab`, после чего воркер присылает
полное зеркало и закрывает устаревшую отслеживаемую вкладку. Это же чинит случай «новый скан при
открытой старой вкладке».

## FIX-9 — offscreen-тир не может держать слот вечно

`mdOffscreenSend` не имеет таймаута: `chrome.runtime.sendMessage` резолвится только когда документ
**ответит**. Документ, убитый посреди fetch (или потерявший ответ), оставлял `mdTryOffscreenDownload`
навсегда висеть — а он держит один из `maxConcurrentDownloads` слотов, `releaseDownloadSlot` в
`.then()` вызывающей стороны не наступает. Три таких зависания = потолок зафиксирован, все остальные
строки «pending» без единой ошибки в логе (ровно форма дампа 2026-09-12). Добавлен
`mdOffscreenFetchBounded` с потолком 180 с: он щедрый сознательно (у stall-watchdog документа таймер
перевзводится на каждом чанке — медленное, но живое чтение 32 MiB нельзя обрезать), а поздно пришедший
ответ, успевший создать объект-URL, тут же отзывается. FF-тир не затрагивается (его там нет).

## FIX-10 — причина смерти перестаёт быть догадкой

`chrome.runtime.onSuspend` (+`onSuspendCanceled`) — единственная точка, где Chrome сам говорит, что
остановка была **проактивной** (idle-таймер или лимит на операцию; при краше и перезагрузке не
вызывается). В обработчике: немедленный flush снапшота и строка
`worker suspending now (lived Ns) — session snapshot written for recovery`. Вместе с уже имеющимся
`previous gen N ended (lived Ns)` это разделяет три сценария без догадок: ~30 с → idle; минуты →
лимит/краш; секунды → перезагрузка расширения/браузера.

## Ошибки и «очередь не опустела штатно» (проверено и закрыто)

ФИКС-7 добавляет новый автоматический путь завершения сессии, поэтому от него отдельно
требовалось, чтобы **любая ошибка давала определённое состояние, а не полу-живую сессию**.

### Пути, которые снимают снапшот

| Путь | Что делает код |
|---|---|
| Естественный дренаж | `checkAllQueuesEmpty` → `contentScanDone` → `scanInProgress=false` + `mdFlushSession()` → `remove` |
| «Cancel All»/stop | `handleStopScanning` → `mdDropSessionSnapshot()` |
| Перезагрузка/обновление расширения | `onInstalled` → `mdDropSessionSnapshot()` (+ Chrome сам чистит session-storage) |
| Закрытие браузера / отключение расширения | Chrome |
| Новая сессия при живом снапшоте | `handleOpenDownloadProgress` → `mdFlushSession()` (снапшот замещается своим) |

### Ошибки: что происходит теперь

- **Исключение внутри восстановления.** Было: `.then(...)` с `catch` глушил ошибку, но состояние
  оставалось частично применённым — строки `pending` без очереди + keepalive, будивший воркер вечно
  (ровно та заморозка, которую FIX-7 убирает). Стало: `mdAbortRecovery(err)` — сессия закрывается,
  снапшот удаляется, все нетерминальные строки→ `failed` + «Session recovery failed — start the scan
  again» (видно и есть Retry). **`activeDownloads` не обнуляется сознательно**: уже запущенные
  кallback-и adoption могут ещё вернуть свои слоты, и обнуление увело бы счётчик в минус (правка N-19).
- **Гонка «новый скан стартовал, пока читался снапшот».** Чтение из `storage.session` асинхронное;
  если контент-скрипт открыл новую сессию за эти миллисекунды, она уже владеет состоянием и могла
  записать свой снапшот. Теперь: `if (scanInProgress) return;` перед применением (старый снапшот не
  затирает живой скан), а удаление ключа в ветке «сессия завершена» тоже защищено условием
  `if (!scanInProgress)` — иначе гонка удаляла бы _свежий_ снапшот новой сессии.
- **Ошибка записи снапшота** (квота, недоступный storage): глушится в `.catch`, сессия просто не
  восстанавливаема в следующий раз; скан идёт как до FIX-7. Флаг `mdPersistBusy` не может заклинить:
  `done()` гарантирован и `.catch`, и внешним `try`.
- **Повреждённый снапшот/строка**: версия `v !== 1` → игнор; строка без строкового `url` или с чужим
  типом задачи → пропускается (type-guard до любых операций). `fileKey`/`mediaHashKey` не бросают
  (`try/catch` внутри, проверено отдельно).
- **Атомарность**: `storage.session.set` пишет значение ключа целиком — после падения воркер видит
  либо старый снапшот, либо новый, промежуточного состояния нет.

### Остаётся открытым: D-9, «зомби-сессия» (не является регрессом FIX-7)

Если контент-скрипт не пришлёт `done` (вкладка закрыта / навигация / смерть вкладки), то `contentScanDone`
остаётся `false`, очереди пусты, счётчики нулевые — и `checkAllQueuesEmpty` не закрывает сессию.
Следствие (существовало и до FIX-7): alarm `md-session-keepalive` будит воркер каждые 30 с, пока
жива сессия браузера, а строки остаются `pending`.
Таймаут «нет работы дольше N — закрываем сессию» **сознательно не добавлен**, и вот почему (ниже —
измеренные числа, а не догадка).

#### Что измерено в коде: ожидания при скане

| Ожидание | Значение | Где |
|---|---|---|
| Ожидание lazy-load / догрузки DOM | **0 мс — ожидания нет вообще** | `PVI.downloadAll` делает ОДИН `doc.querySelectorAll('a[href], img, video, [onclick], button, [role="button"]')` в момент нажатия. Ни скролла, ни `MutationObserver` для скана, ни повторных проходов (наблюдатель в 4682 — атрибутный, для оверлея Imagus) |
| Пре-фильтр DOM (видимость, стоп-слова, resolve-кандидат) | 100 элементов за тик, **50 мс** между тиками | `chunkSize = 100`, `setTimeout(processChunk, 50)` |
| Резолв одного элемента через движок | **`resolutionTimeout`, по умолчанию 8 с** на элемент | `setTimeout(() => onResolved(null), (cfg.da.resolutionTimeout \|\| 8) * 1000)` |
| Пауза между элементами очереди | 10 / 100 / 150 мс (по веткам) | `setTimeout(PVI.processNextInQueue, …)` |
| Fetch в путях галереи/резолва | 30 с | два `AbortController`-таймаута |
| Referer-ретрай в SW | 30 с | watchdog в `triggerRefererDownload` |
| Зависшая загрузка (stall) | 60 с | `STALL_MS` (FIX-6) |
| Ответ offscreen-документа | 180 с | `MD_OFFSCREEN_ANSWER_MS` (FIX-9) |

Практический вывод: **тишина в очереди ограничена сверху `resolutionTimeout` на элемент** (контент
шлёт минимум одно сообщение на разрешённый элемент и на каждый чанк пре-фильтра), поэтому «спящая»
сессия не может быть следствием медленного рендера lazy-load.

#### D-9 (сделано): спрашиваем Chrome, а не гадаем по таймеру

Первая версия выводила «страница молчит» из таймера («нет слова N минут»). Такой порог невозможно
обосновать: Chrome тормозит таймеры в скрытых вкладках, здоровый скан может законно замолчать, а
решение по догадке отменяло бы живую работу (задачи после `scanInProgress=false` помечаются
`canceled`). Эта версия **вырезана**; вместо неё — один вопрос к Chrome: без порогов, без учёта
живости в `handleMessage`, без новой строки в логе.

- `mdProbeInitiatorTab()` вызывается из alarm keep-alive — единственного периодического тика при
  открытой сессии — и действует только в одном состоянии: сессия открыта, `contentScanDone` нет и
  **в полёте ничего нет** (`mdNoWorkInFlight()`);
- нет инициатора вообще → `mdConcludeAbandonedScan()` сразу; иначе `chrome.tabs.get(id)`;
- **вкладка существует → делать нечего**: страница жива и ещё пришлёт `done`; заморожена она или просто
  медленная — это решение её пользователя (страница сама предупреждает «Do not leave this page until
  scanning is complete!», а строка сохраняет кнопку Retry). Никакого таймера, который мог бы отменить
  живую работу;
- **вкладки нет → `mdConcludeAbandonedScan()`**: `contentScanDone = true` (никто больше не пришлёт
  `done`), `downloadInitiatorTabId = null`, ложное «All downloads completed» подавляется, сессия
  отдаётся обычному `checkAllQueuesEmpty` и закрывается, как только доиграют очереди. Строки **не**
  фаталятся: браузерным загрузкам страница не нужна, а тем, кому нужна (referer-ретраи), достаётся
  видимый `Referer retry unavailable` с Retry.

`mdCheckInitiatorGone()` (путь неудачного сообщения) сведён к той же функции — одна реализация смысла
«страницы больше нет». Решение принимается в пределах одного тика (30 с), а не после выдуманного окна
молчания; замеры, которые это обосновывают, — в таблице выше (тишина в очереди ограничена
`resolutionTimeout` на элемент, ждать «минутами» нечего).

Свойства, залоканные тестами: проба **не срабатывает при любой работе в полёте** и после
`contentScanDone`; путь «вкладки нет» **не фаталит строки** и не объявляет завершение; и отдельный лок
— в коде нет ни одного упоминания вырезанного таймерного дизайна
(`MD_CONTENT_SILENCE_MIN_MS` / `mdContentSeenAt` / `mdPageSilentMs` / `mdNoteContentSeen` /
`MD_PAGE_MSG_CMDS`), чтобы он не вернулся незамеченным.

#### Поправка к обоснованию (после вопроса владельца, 2026-09-12)

Формулировка «пауза в несколько минут нормальна для замороженной вкладки» была слишком широкой, и вот
что об этом говорит код:

- пользователя предупреждают **на странице** — `_updateDownloadAllStatus` рисует плашку
  `'Do not leave this page until scanning is complete!'` (`content.js:4774`), а на время скана
  включается аудио-keep-awake (`_startKeepAwake`, зацикленный silent WAV). То есть ожидаемое поведение
  — «пользователь не уходит», и заморозка вкладки — это уже нарушение инструкции, а не штатный режим;
- промежуточный случай — пользователь переключился в другое окно (страница скрыта, но не мертва):
  Chrome тормозит таймеры до ~1 раза в минуту, сообщения при этом доходят. Именно из-за него никакой
  порог не годится — решение «вкладки нет» теперь принимает Chrome, а не таймер (см. D-9 ниже);
- **настоящая дыра нашлась рядом** и не связана с догадками: `groupAnalysisComplete` отправляется в
  `catch`, который безоговорочно обнулял `downloadInitiatorTabId` (service-core.js:2909). Если
  сообщение не прошло по временной причине (занятый/замороженный рендерер), мы теряли инициатора
  навсегда — а контент-скрипт именно этого сообщения и ждёт, чтобы отправить закрывающий `done`.
  Итог: сессия остаётся открытой навсегда при **живой** странице, и никакие ретраи больше не работают.
  Исправлено: `mdCheckInitiatorGone()` — спрашивает у Chrome, существует ли вкладка:
  - вкладка есть → id сохраняется (одно неудачное сообщение — не доказательство);
  - вкладки нет → `downloadInitiatorTabId = null` **и** `contentScanDone = true`: никто больше не
  пришлёт `done`, поэтому скан заключается здесь, очереди доигрываются браузерными загрузками
  (они страницы не требуют), и сессия закрывается сама. Строки, которым нужна страница
  (referer-ретраи), падают видимо — 'Referer retry unavailable' с Retry, без зависания.

**D-11 — решено НЕ делать** (по критерию «максимум пользы при минимуме сложности»). `_stopKeepAwake`
выключается, когда скан завершает **контент-скрипт**, а SW после этого ещё может нуждаться в странице
(referer-ретраи на групповых элементах). Удержание keep-awake до конца сессии помогло бы только
**полностью замороженной** вкладке — то есть случаю, в который пользователь зашёл сам, вопреки плашке
на странице. Цена: новое сообщение SW→контент, правка жизненного цикла аудио и проверка UI (Chrome
рисует значок звука на вкладке). При неудаче строка и так уходит в `failed` с Retry, поэтому машинерия
не строится. Вернуться к вопросу — только если живые тесты покажут такие случаи.

#### Найдено попутно: повторный скан не помнит уже скачанное (D-10, к обсуждению)

`handleOpenDownloadProgress` вызывает `resetMassDownloadSession()`, который **чистит
`globalProcessedUrls`**. Значит второй скан той же страницы (например, прокрутили галерею и нажали
хоткей ещё раз, чтобы добрать то, что догрузилось) заново скачает уже скачанные файлы, а
`conflictAction: 'uniquify'` создаст рядом `name (1).jpg`. Данных не теряется, но папка засоряется.
Это отдельное решение (персистить дедуп-ключи между сессиями — и получить риск пропустить файл,
который пользователь хочет скачать повторно), поэтому вынесено в очередь, а не исправлено молча.

### ROWS-1 (2026-09-12, вечер) — окно прогресса врало: порядок вытеснения строк

**Симптом владельца:** «на странице прогресса в основном ошибки, 17 completed хотя по факту загружено
37 файлов». Лог сам себе противоречил: `downloaded=30` против `completed=17` при ровно 100 строках.

**Разбор (данные, не догадка).** Архив логов даёт однозначную пару: ниже потолка счётчик и строки
совпадают точно (34/34, 45/45, 33/33, 29/29), на потолке — расходятся (117/90, 77/44, 30/17). Значит
дело не в потере состояния, а в правиле вытеснения: и SW, и вкладка сортировали строки как
`{ completed: 0, skipped: 1, failed: 2, … }` и удаляли `slice(0, excess)` — **первыми гибли самые
старые `completed`**. Строки, которые ПОДТВЕРЖДАЮТ скачивание, выбрасывались раньше любой ошибки, а
плитки считались по этой же урезанной таблице: отсюда и «в основном ошибки», и 17 вместо 30.

**Решение.** `mdEvictOldestRows(table, maxRecords)`: сначала вытесняется ЗАВЕРШЁННАЯ строка (живая
должна продолжать получать обновления в существующую запись) и самая старая внутри группы — обычное
скользящее окно, ни один статус не удаляется систематически. Та же логика встроена во вкладку
(у неё своя копия таблицы) и зафиксирована локом на текстовое совпадение набора статусов.
Плюс убрана лживая подача: `To Download` → `Rows in List` (это был `items.length - skipped`),
`Completed` → `Completed in List`, строка-объяснение под плитками (`#listNote`), и в Save Log
`Rows in this log: N (list capped at da.maxProgressRecords=…)` рядом со `Stats (scan totals …)`.

**Не лечится этим:** доля 403 на `wimg.rule34.xxx` (и в фильтре, и в самой загрузке браузером) —
она высокая с 09-08 и к батчу D-1…D-7 отношения не имеет; нужен живой замер (ROWS-2 в аудите).

### SUPERSEDE-1 (2026-09-12, ночь) — «46 ошибок» при 42 скачанных файлах: строка на ПОПЫТКУ вместо строки на ПУНКТ

**Симптом владельца:** «реально загружено 42 файла… ссылки server error bad content ведут на реальные
404 not found». ROWS-1 починил вытеснение, но не смысл счётчиков: в логе
`log/imagus-mass-download-log-2026-09-12T19-07-38.txt` — `downloaded=42`, строк `COMPLETED` тоже
**42** (все 42 превью получили файл), но `FAILED` = **46**.

**Разбор (по данным лога, не по догадке).** 46 «ошибок» — это строки-ПОПЫТКИ, а не потерянные файлы.
Проверка — не по basename (basename с разным расширением бывает РАЗНЫМ файлом: в этом же логе
mp4-видео и jpg-превью делят basename), а по цепочке попыток: **44 из 46** failed-строк — это URL,
присутствующие в `attempts`-цепочке терминальной строки ТОГО ЖЕ пункта (оставшиеся 2 — крайние
кандидаты двух пунктов, которые в старой версии вообще не попадали в цепочку). Механика: пункт идёт
по кандидатам (`images/x.jpg` → 404 → `images/x.png` → 200), и**каждый** мёртвый кандидат оставался в
таблице как `failed` навсегда, хотя файл пункта скачался из следующего кандидата. Отсюда «в основном
ошибки»: из 42 пунктов файла не получили **2** (`ac05b62d…@1882`, `da01bfd7…@2946` — все 4 кандидата
404, что владелец и подтвердил в браузере), а не 46.

**Второй дефект в той же строке — текст.** Терминальная строка писала
`Server error: SERVER_BAD_CONTENT - trying alternate URL`, хотя (а) на этом шаге никакого «trying» уже
нет — цепочка исчерпана; (б) `SERVER_BAD_CONTENT` у Chromium — это **HTTP 404**
(`HandleSuccessfulServerResponse`, `components/download/internal/common/download_utils.cc`: 404 (а также
204/205, у которых нет тела) → `SERVER_BAD_CONTENT`, 403 → `SERVER_FORBIDDEN`, 401/407 →
`SERVER_UNAUTHORIZED`, остальные 4xx/5xx → `SERVER_FAILED`). Комментарий в коде утверждал, что Chrome
отдаёт и 403, и 404 как `SERVER_FORBIDDEN` — **это неверно**, и именно из-за него честный 404 выглядел
«ошибкой сервера».

**Решение (одна точка решения на всю цепочку).**
- `mdSupersedeAttempt(url, reason, task)` вызывается из `advanceToNextCandidate` и
  `requeueNextCandidateForFilter`: мёртвый кандидат помечается `skipped` + `superseded` с причиной
  «… — superseded: the item continued with another candidate URL». Строка НЕ удаляется: остаются её
  URL, её причина и **её кнопка Retry** (в SW `retryDownload` статус-агностичен, дедуп для ретраев
  отключён). Это принципиально: в живом примере пункт `ccaeb…` отдал sample 431 КБ, а полноразмерный
  кандидат 404-ил, и Retry этой строки — единственный способ дожать полный файл. Отменённые
  пользователем строки не трогаются (`status === 'canceled'` — вердикт владельца, не наш).
- `mdItemFailedText(task, base)` во всех 9 терминальных точках: вердикт пункта говорит
  «all N candidate URLs failed», а не «trying alternate URL».
- При исчерпании цепочки `advanceToNextCandidate` сам пишет последнюю попытку в `_attempts`: теперь
  цепочка в Save Log полная (раньше последний кандидат в неё не попадал — ровно те 2 строки).
- Флаг `superseded` проброшен через `serializeProgressEntry` / `updateDownloadProgress` во вкладку:
  Retry рисуется для `failed | canceled | superseded`; Save Log печатает, сколько строк вытеснено и что
  потерянными файлами они не являются.

**Что НЕ теряется (ответ на вопрос владельца).** Решение принимается по цепочке САМОГО пункта, поэтому:
пункт скачался ⇒ его мёртвые попытки — не ошибки; пункт не скачался ⇒ остаётся ровно ОДНА
`failed`-строка с честным текстом. Строки и URL сохраняются (в таблице — как `skipped` + Retry, в логе —

### ROWS-3 (2026-09-12, живой прогон 19:46) — объяснение в Save Log не срабатывало на полном списке

Прогон той же страницы после правки дал ровно ожидаемое: `completed=40`, `failed=2` (оба — честный
текст «all 8 candidate URLs failed»), 58 `skipped` (superseded). Владелец при этом увидел «37 файлов»
и расхождение с логом — разобрано сверкой с диском (`D:\Arx\Software Downloads`): все 40 файлов на
месте, 37 из них с mtime в окне сессии, а 3 записаны как `… (1).png|jpg`, потому что файлы с теми же
именами уже лежали с 08:12 (Chrome `uniquify`); 41-й файл (`21e5fc73….mp4`) — строка, вытесненная
потолком 100.

**Дефект подачи найден именно здесь:** строка-объяснение сравнивала **общее число строк**
(`items.length`) с `downloaded + skipped`, поэтому на полном списке (100 из 100) молчала всегда —
ровно тогда, когда и нужна. Исправлено на чистую `mdLogCapNote(byStatus, stats)`: сравнивает
**completed-строки** с живым счётчиком и прямо говорит, что файлы на диске. Гейты: `repro-row-window`
33/33 (19:46 → «1», 18:57 → «13», молчание при 34/34 и 0/0, регрессия «сравнение с `items.length` не
возвращается»), лок `ROWS` в смоуке, мутация (всего 16 из 16).

### RESUME-1 (2026-09-13, ночь) — «Scan complete… Analyzing 82 complex items» навсегда (живой прогон 19:58)

**Что увидел владелец:** скан встал на `Scan complete. Analyzing 82 complex items...` и не двигался
минутами; фактически скачано 8 файлов из 42. Позже то же самое повторилось на другой странице
(«Analyzing 82 complex items», 8 из 42) — то есть баг воспроизводимый, а не случайный.

**Что в логе** (`log/imagus-mass-download-log-2026-09-12T19-57-59.txt`): сессия оборвалась на 36-й
секунде — сервис-воркер перезапустился. Дальше в логе НЕТ ничего: ни валидаций, ни загрузок, ни
статусов. Загрузки не «зависли» — **работать было некому**.

**Корень (два состояния разъехались при перезапуске, а не «медленная сеть»):** FIX-7 восстанавливает
**очереди и таблицу** из снапшота, но НЕ восстанавливает **диалог со страницей**. Конец скана на
странице — это промис: страница отдаёт группы (`resolveAndDownloadGroups`) и ждёт ответного
`groupAnalysisComplete`; только после него она закрывает скан (`updateStatus{done:true}`). Запрос, на
который отвечал старый воркер, умер вместе с ним, а новый этот запрос никогда не получал — значит и
ответить не мог. Очереди к этому моменту пусты (группы уже отправлены, одиночные пункты уже
загружены), поэтому `mdNoWorkInFlight()` истинно и `mdProbeInitiatorTab` (D-9) доходил до ветки
«вкладка жива» — и ждал вечно. D-9 закрывал это состояние только для ЗАКРЫТОЙ страницы.

**Правка (три части, оба дерева):**
1. **Спросить страницу.** В конце `mdApplySnapshot()` — `mdAskInitiatorToResume()`:
   `chrome.tabs.sendMessage(tab, {cmd:'resumeGroupAnalysis'})`. Страница держит группы в памяти, и
   воркер отвечает на них обычным путём. Если страница ещё идёт по DOM (`downloadAllQueue` не пуст),
   она НЕ молчит, а подтверждает `resumeGroupAnalysisAck` — иначе живая, но занятая страница выглядела
   бы мёртвой, и воркер завершил бы здоровый скан, который сам же должен был продолжить.
2. **Ограниченное окно ответа.** `MD_RESUME_ANSWER_MS = 20000`: живой content script отвечает
   мгновенно (он же присылает `updateStatus`/`done`), осиротевший (расширение перезагрузили, вкладка
   осталась открытой) не ответит никогда. Молчание дольше окна ⇒
   `mdConcludeAbandonedScan('the page did not answer the resume request…')`: скан завершается, сессия
   доигрывается, строки сохраняют Retry — как D-9 для закрытой вкладки, но теперь и для живой
   неотвечающей.
3. **Одно окно на все «живые» ответы.** Окно сбрасывают: `handleResolveGroups` (страница прислала
   группы), `handleUpdateStatus{done}` (страница закрыла скан сама) и `mdResumeAck` (страница
   подтвердила «жив, ещё иду по DOM»). `mdResumeAck` не трогает ни очереди, ни сессию, ни
   `downloadInitiatorTabId`.

**Почему повторная отправка групп безопасна:** снапшот восстанавливает дедуп-ключи, а к ним добавлена
страховка от дебаунса — терминальные СТРОКИ (`completed`/`skipped`/`canceled`) сеют те же ключи
(`fileKey` + `mediaHashKey`) сразу, не дожидаясь отложенной записи. Повторно отправленная группа не
может скачать уже скачанное.

**Чего правка НЕ делает (осознанно):** замороженную/выгруженную вкладку, которая проснётся позже,
воркер не «дожимает» принудительно — сессия уже завершена, файлы доедут (дедуп на месте), но страница
останется со своим статусом и `downloadAllActive=true` до перезагрузки. Причину заморозки создал сам
пользователь (страница прямо предупреждает не покидать её до конца сканирования). Принудительно
закрывать скан в этом случае нельзя: `stopScanning`/`groupAnalysisComplete` отменили бы DOM-обход
живой вкладки и потеряли бы её оставшиеся элементы — а это уже потеря функционала, а не косметика.

### PERF-1 (2026-09-21) — **ОТКАЧЕНО** (коммит `5918995` откатан до `a01ec9b` по факту живого теста)

**Факт:** на сборке с телеметрией обхода (`5918995`, версия 2026.9.21.3) скан перестал запускаться —
не стартовал ни по Ctrl+Q, ни по кнопке popup (загрузки из окна галереи работали). После отката на
`a01ec9b` (версия 2026.9.21.2 — та сборка, что дала последний рабочий лог на 175 файлов) скан запускается.
Владелец подтвердил: виноват именно этот коммит. Рабочее дерево байт-в-байт равно `a01ec9b`.

**Что было в коммите:** только измерения (счётчики стоимости обхода: `_mdWalkPerfNew`/`_mdWalkBucket`/
`_mdWalkBook`, `scanId`, белый список `mdScanWalkForLog` в воркере, печать `walk cost (scan sN)` в Save Log).
Диффом проверено: в `content.js` удалено ровно 8 строк — семь `setTimeout(PVI.processNextInQueue, N)` и
 строка полей `_mdDiagInit`; в `service-core.js` и `download-progress.js` — чистые добавления.

**Единственное структурное изменение РАНТАЙМА — замена прямого перевзвода обхода**
`setTimeout(PVI.processNextInQueue, N)` → обёртка `PVI._mdWalkDelay(N)`. Это и есть подозреваемый: если
`PVI._mdWalkDelay` в момент вызова недоступна, обход умирает на первом же элементе (элементы собраны,
никаких загрузок, плашка не оживает), а ошибка видна ТОЛЬКО в консоли user-script мира — то есть в
обычном DevTools она не показывается. Почему статически всё выглядело целым (`node --check`,
`md-marker-check`, исполняемые локи) — вопрос открытый, и я его не закрыл; гадать не буду.

**Правило для повторного захода (обязательное):**
1. Планировщик обхода НЕ трогать. `setTimeout(PVI.processNextInQueue, N)` остаётся на месте как есть;
   измерения добавляются только рядом — счётчики и исходы в точках `_mdBook(...)`, а `delayMs` считается
   как сумма известных значений на выходе, а не обёрткой вокруг перевзвода.
2. Ставить по одному шагу и после КАЖДОГО делать живой прогон (скан запускается, файлы идут) — только
   тогда следующий шаг. Сначала счётчики, потом `scanId`, потом печать в Save Log, потом белый список.
3. Версию бампить ПЕРЕД прогоном и читать `Version:` в логе — иначе сборка не опознаётся.

**Отдельно: два дефекта в путях ЗАПУСКА, найденные при разборе (оба есть и в `a01ec9b`, т.е. НЕ из этого
коммита, оба подтверждены живьём):**

  `Uncaught ReferenceError: sendResponse is not defined`. По коду: `PVI.onMessage: function (d)` — один
