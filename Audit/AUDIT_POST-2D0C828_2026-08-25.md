## 🔴 P1 — `doSave`: ранний/двойной `finish()` убивает standalone-сессию

`src-mv3-overlay/content/content.js:675-738` (на момент аудита), взаимодействует с `mass-download/service-core.js:283-290` и `:582-596`.

`pendingParts = (batch>0?1:0) + (links>0?1:0)`, но `finish()` срабатывает не тот раз и не в то время:

- **`links=0, 0<batch≤25`** — `finish` корректно срабатывает из последнего чанка, затем **ещё раз** из `_mdChain.then(finish, finish)`: цепочка не использовалась и осталась `Promise.resolve()` → микротаск → `pendingParts` уходит в −1 → тело `finish` выполняется дважды (двойной `updateStatus{done:true}`, двойной `clearSelectionUi`) — косметика.
- **`links>0, batch=0`** (все выбранные — page-links без превью, e-hentai-кейс) — `sendChunk(0)` с пустым batch вызывает `finish()` **синхронно в момент клика**, до какого-либо резолва. По SW: `handleUpdateStatus` ставит `contentScanDone=true` → через 100 мс `checkAllQueuesEmpty` видит пустые очереди → `scanInProgress=false`, keepalive снят, «allDownloadsComplete». Первый `downloadMass` прилетает через сотни мс/секунды (резолв сериализован, сеть) → `handleDownloadMass` сознательно не реанимирует сессию (Audit N-02) → фильтр помечает всё `canceled` (`service-core.js:792-797`) или молча дропает со строкой, зависшей в `scanning` (`:826`). **Фича «resolve on Save» в standalone-режиме не работает.**
- **`links=0, batch>25`** — `done:true` уходит микротаском до хвостовых чанков. На практике выживает (очередь занята на отметке 100 мс), но это нарушение порядка, о котором старый код писал прямо.

В **2d0c828** инвариант был записан в этом же месте: *«Close the standalone session only after the LAST chunk — premature done:true cancels in-flight queue work (N-02)»*. Переписывая `doSave` под links-фазу, модель удалила комментарий вместе с семантикой; новый комментарий («Everything is queued BEFORE this lands») неверён для links-фазы.

**Почему могло пройти живое тестирование:** если превью в сетке уже прогрузились через резолвер, `mdByCell` относит их к `batch` (прямые URL), `links` пуст — всё уходит мгновенно и выживает. Ломается ровно «холодный» путь (выделил → сразу Save). При живом скане (`scanWasActive=true`) `done` не шлётся вообще — тоже работает.

## 🟠 P2 — `paceGrid`: утечка слотов в stage-2/3 → коллапс «max 3 concurrent»

`content.js:488-529` (на момент аудита). В `onFail` для stage 2/3: `active++` → `loadViaResolve/loadViaPageFetch` → `settle(m,false)` — инкремент и декремент гасят друг друга мгновенно, а цепочка при завершении делает **свой** `settle` (`active--`) без парного `active++`:

- успех резолва → `armLoad` + `src=` → `onOk` → `settle` → −1;
- неудача (`!cands`, `!isConnected`, catch, CORS) → `settle` → −1;
- page-fetch: `onload`, `onerror`, `catch` → −1.

Каждая эскалация в stage 2/3 — гарантированный −1. `active` уходит в минус, `while (active < MAX_ACTIVE)` запускает сверх лимита, ошибки грузятся лавиной → ещё эскалации → ещё дрейф. Лимит «3 параллельных, щадящих hath.network/e-hentai» разрушается именно на тех хостах, ради которых задуман (риск 429). Не дедлок, а противоположность. Класс ошибки «slot release без парного take» из истории проекта (watchdog double-release, `createObjectURL`-лик 2026-08-22).

Дополнительно: в stage 1 таймер-retry при `!m.isConnected` делает `settle(m,false)` без `active++` — та же утечка (−1), редкий случай (сетку закрыли в окне retry 1500 мс).

Для альбомных page-links приемлемо.

## Решения слабой модели — где она права

- **`_mdSerialized`** — сериализация всех вызовов резолвера через одну promise-цепочку из-за единого `PVI.timers.resolver` у движка (`a00a639`) — правильное прочтение внутреннего устройства.
- **Прямой вызов `PVI.resolve`** с честным контрактом params (`$:[url, ...groups]`, свежий fake-элемент, без `IMGS_TRG`) — 4 итерации отлова (`4b1dea5`, `59172ed`), финал соответствует `find():2055-2064`.
- **«What you see is what you save»** (`mdByCell` из network-proven `dataset.mdSrc`, исключение `blob:` — SW не может их fetch) — прагматично и тонко.
- Отказ от groups-pipeline в `44c7fca` — упрощение в верном направлении; негативный кэш 30 с + сброс перед каждым Save; чанки 25/10мс.
- **Порт 8.20** — лучшая часть: план WP-1..4, решения R1-R7, осознанный отказ от `chrome.downloads.onDeterminingFilename` (ломал все загрузки браузера, upstream #132/#134/#69) в пользу префикса каталога в `params.filename` с посегментной санитизацией под Windows — решение лучше апстримного. Все 14 mass-download switch-cases и `importScripts` пережили порт; оверлей-фиксы reapplied; FF-дельта минимальна.
- Диагностические коммиты не оставили мусора — в финале только 3 уместных `console.warn`.
